# W-9. 웹 초개인화 모듈 - 관리자 운영

근거 문서: `docs/redesign-v2/00-master-spec-v1.md`(§27), `docs/redesign-v2/01-module-split-plan.md`(§4-A W-9). [W-8 §7](W-8-api-and-db-changes.md)에서 넘긴 `ADMIN`/`OPERATOR` 권한 구분 확인과 `DATA_REVIEWER` 마이그레이션 결정을 다룬다. 이 문서는 `apps/admin`(관리자 포털) 자체의 화면 설계서가 아니라 - **웹 모듈이 관리자에게 어떤 데이터·기능을 노출해야 하는지 범위만 정의**한다([W-1 §1](W-1-scope-and-user-types.md)에서 이미 "참가업체·운영자는 admin 소관"이라고 확정한 경계를 여기서 구체화).

## 1. `ADMIN` vs `OPERATOR` 권한 구분 - 확인 결과

`backend/app/services/*` 전체를 검색한 결과, `role_code`가 `'ADMIN'`/`'OPERATOR'`/`'EXHIBITOR'` 값으로 실제 권한 분기하는 서비스 로직이 **현재 존재하지 않는다** - `profile.role`/`profile.user_role` 테이블은 스키마만 정의돼 있고 아직 어떤 API도 role 기반 인가(authorization)를 구현하지 않았다.

**결론**: [W-8 §3](W-8-api-and-db-changes.md)의 "실제 권한 차이를 확인한 뒤 매핑을 정한다"는 전제가 성립하지 않는다 - 확인할 기존 동작 자체가 없으므로, 매핑은 관찰이 아니라 **이번 재설계에서 새로 정의**해야 한다. 다음을 웹 모듈 관점의 잠정 정의로 채택한다.

| role_code(기존) | 마스터 스펙 역할 | 웹 모듈이 노출하는 권한 |
| --- | --- | --- |
| `EXHIBITOR` | `EXHIBITOR_ADMIN` | 자사 업체 정보 열람(등록은 아님 - 등록은 C-2 소관), [W-7](W-7-buyer-matching-consultation.md) 상담 요청 수락/거절 |
| `OPERATOR` | `EVENT_ADMIN` | 사전등록 연계 상태 확인(§2), 바이어 검증(§4) |
| `ADMIN` | (마스터 스펙 범위 밖 - 테넌트 최상위 관리) | 웹 모듈 화면에 노출하지 않음 |
| (신규) | `DATA_REVIEWER` | 업체정보 승인만(§3) - `EVENT_ADMIN`의 하위 집합 |

**`DATA_REVIEWER` 마이그레이션 여부 - 최종 결정**: 위 표에서 보듯 `DATA_REVIEWER`는 "업체정보 승인"이라는 좁은 단일 기능만 가지며, 이는 이미 `EVENT_ADMIN`(`OPERATOR`) 권한의 부분집합이다. **별도 role_code를 신설하지 않고, `EVENT_ADMIN`(`OPERATOR`) 내부의 세부 권한 플래그로 처리한다.** 이유: role_code는 "역할"이라는 굵은 단위이고, "업체정보 승인만 가능·다른 건 불가"는 역할이라기보다 권한 스코프의 문제이므로, `profile.role` 테이블에 행을 추가하기보다 인가 로직(서비스 계층)에서 세분화하는 편이 확장에 유리하다 - [W-8 §1](W-8-api-and-db-changes.md) 항목 2번("중간 우선순위")을 이 결정으로 대체하고, 해당 마이그레이션은 불필요한 것으로 재분류한다.

## 2. 사전등록 연계 (관리자 관점)

- [W-2 §1-1](W-2-user-journey.md)에서 "배치 임포트"로 가정한 사전등록 연계의 진행 상태(성공/실패 건수)를 확인하는 화면. 웹 모듈은 임포트 결과 조회 API만 제공하고, 임포트 자체를 트리거하는 배치 잡은 C-7(공통 인프라)의 워커가 담당한다.

## 3. 업체정보 승인

- 웹 모듈 자체의 기능이 아니라 공통 플랫폼 C-2("업체정보 수집·AI 구조화... 운영자 승인")의 책임이다. 웹 모듈 관점에서는 "승인되지 않은 업체는 추천·검색 결과에 노출되지 않는다"는 소비자 측 제약만 확인하면 된다 - `exhibition.recommendable` 레지스트리가 이미 이런 승인 상태 필터링을 전제로 설계돼 있는지는 C-2에서 확정.

## 4. 추천 대상 관리 · 바이어 검증

- 추천 대상 관리(어떤 업체를 추천 후보 풀에 포함할지)는 C-1/C-2 소관.
- 바이어 검증: `profile.BuyerNeed.business_email_verified`/`company_verified`([W-4 §4](W-4-profile-model.md))가 이미 이 목적을 위한 컬럼이다 - 관리자가 이 두 플래그를 수동으로 켜는 화면만 있으면 되고, 신규 스키마는 필요 없다.

## 5. 기본 통계

- 웹 모듈이 관리자에게 노출하는 통계는 다음 3개로 한정한다(§27, 마스터 스펙에 구체적 지표가 명시되지 않아 W-2~W-8에서 다룬 데이터만으로 산출 가능한 것 위주로 확정): 사전등록 연계 건수, 프로파일 완성도 분포(`completeness_score`), 상담 요청/수락 건수([W-7](W-7-buyer-matching-consultation.md)). 복잡한 대시보드·BI 연동은 마스터 스펙 §56 제외목록의 "복잡한 MLOps" 수준의 확장 항목으로 분류하고 MVP에서 제외한다.
