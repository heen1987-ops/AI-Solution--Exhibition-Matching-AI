# W-1. 웹 초개인화 모듈 - 서비스 범위·사용자 구분

근거 문서: `docs/redesign-v2/00-master-spec-v1.md`(§1, §2.1, §7~16), `docs/redesign-v2/01-module-split-plan.md`(§2.1, §4-A W-1). 재설계 진행순서(1차: 웹 W-1~W-10)의 첫 산출물이다.

## 0. 이 문서의 목적과 범위

W-1은 "무엇을 만들 것인가"만 확정한다 - 화면(W-3), 프로파일 필드(W-4), 점수식(W-5), API·DB(W-8)는 이후 단계에서 다룬다. 이 문서가 답해야 하는 질문은 셋뿐이다.

1. 웹 초개인화 모듈이 서비스하는 사용자는 정확히 누구인가 (경계 포함)
2. 각 사용자에게 행사 전·중·후 어느 시점에 무엇을 제공하는가
3. 지금까지 만든 백엔드(`identity`/`profile`/`matching`/`exhibition` 스키마)의 어떤 부분이 그대로 재사용되고, 어떤 부분이 이번 재설계로 바뀌는가

## 1. 웹 모듈의 서비스 대상 (기존 실장 대비)

마스터 스펙 §7(사용자 역할)과 기존 스키마를 대조하면 다음과 같다.

| 마스터 스펙 역할 | 정의 | 기존 스키마 대응 | 변경 필요 여부 |
| --- | --- | --- | --- |
| `GENERAL_REGISTERED` | 사전등록 일반 사용자 | `profile.user_profile.user_type = 'GENERAL_VISITOR'` | **이름 불일치만 있음.** 값 자체를 변경할지, API 레이어에서 매핑만 할지는 W-8에서 결정(§6 참고) |
| `BUYER_REGISTERED` | 사전등록 바이어 | `profile.user_profile.user_type = 'BUYER'` + `profile.buyer_need` | 그대로 재사용 가능 |
| `GUEST_WEB` | QR 인계 또는 게스트 웹 사용자 | `profile.guest_session` + `user_id IS NULL`인 `user_profile` | 그대로 재사용 가능 - 단, 지속 프로파일을 만들지 않는다는 마스터 스펙 원칙(§45.2, §56 "키오스크 장기 프로파일 제외")과 구분해야 한다(§3 참고) |
| `KIOSK_GUEST` | 키오스크 익명 사용자 | **없음** - 키오스크는 별도 모듈(K-*)이 담당 | 웹 모듈 범위 밖. W-1에서는 다루지 않는다 |
| `EXHIBITOR_ADMIN` | 참가업체 관리자 | `profile.user_role`(role_id로 참조하는 역할 테이블) | 이미 role 테이블 구조가 있어 그대로 재사용 |
| `EVENT_ADMIN` | 행사 운영자 | `profile.user_role` | 그대로 재사용 |
| `DATA_REVIEWER` | 업체정보 검수자 | `profile.user_role` (또는 EVENT_ADMIN의 하위 권한) | role 코드 목록에 `DATA_REVIEWER`가 실제로 등록돼 있는지 W-9(관리자 운영)에서 확인 필요 |

**결론**: 웹 모듈이 직접 다루는 사용자는 `GENERAL_REGISTERED`, `BUYER_REGISTERED`, `GUEST_WEB` 3종이다. `EXHIBITOR_ADMIN`/`EVENT_ADMIN`/`DATA_REVIEWER`는 웹 모듈이 아니라 관리자 포털(`apps/admin`) 소관이며, W-9에서 "웹 모듈이 그들에게 무엇을 노출하는가"만 다룬다(예: 참가업체가 자기 업체 통계를 보는 화면은 admin 쪽 문서에서 정의).

## 2. 참가업체·운영자는 왜 웹 초개인화 대상이 아닌가

마스터 스펙 §2.1의 표는 참가업체·운영자를 "업체·제품·거래정보 관리"/"데이터 승인·검색·추천 운영"으로 분류한다 - 이는 "초개인화 추천을 받는" 쪽이 아니라 "데이터를 공급·승인하는" 쪽이라는 뜻이다. 따라서:

- 참가업체 관리자는 웹 초개인화 모듈의 **추천 대상**이 아니라 **데이터 입력자**다. 자기 부스가 얼마나 추천됐는지 보는 통계 화면은 W-1의 "웹 초개인화"가 아니라 관리자·업체 포털(§27.2)의 몫이다.
- 운영자도 마찬가지로 승인·통계 화면만 갖는다.

이 구분을 W-1에서 명시하는 이유: 이후 단계(W-4 프로파일 모델, W-5 추천 로직)에서 "참가업체용 관심 프로파일"이나 "운영자용 추천 점수" 같은 범위 밖 기능을 실수로 설계하지 않기 위함이다.

## 3. GUEST_WEB과 "지속 프로파일 없음" 원칙의 경계

마스터 스펙은 두 가지를 동시에 요구한다.

1. §45.2/§56: 키오스크는 회원가입·장기 프로파일을 절대 만들지 않는다.
2. §23.3: 키오스크 QR로 넘어온 게스트 웹은 "업체 목록 보기·상세·지도 보기·브라우저 내 임시 저장"만 하고, "회원 전환은 선택적으로 제공할 수 있으나 강제하지 않는다."

즉 `GUEST_WEB`은 웹 모듈의 사용자 유형이지만, **키오스크에서 QR로 넘어온 게스트는 여전히 "지속 프로파일이 없는" 상태를 유지해야 한다** - 단지 화면이 키오스크가 아니라 웹이라는 것만 다르다. 반면 사전등록 없이 웹에 직접 방문해 이메일 등으로 가입한 사용자는 `GENERAL_REGISTERED`가 된다.

**규칙**: `GUEST_WEB`은 `guest_session_id`만으로 식별되는 `user_profile` 행이며, `user_id`(인증 계정)로 전환되기 전까지 `EXPLICIT`/`CONFIRMED` 상태의 관심 프로파일을 쌓지 않는다(10.2절 프로파일 상태와 연결 - W-4에서 상세화). 이는 이미 `profile.user_profile`의 `num_nonnulls(user_id, guest_session_id) = 1` CHECK 제약(exactly_one_owner)과 `guest_session`이 익명 세션이라는 기존 설계와 정합적이다 - 스키마 변경 없이 "게스트 프로파일에는 EXPLICIT 관심사를 강하게 쌓지 않는다"는 서비스 규칙만 W-4/W-5에 추가하면 된다.

## 4. 행사 전·중·후 제공범위

마스터 스펙 §8.1("행사 전·중·후에 전달")과 §54 Phase별 완료기준을 종합해 사용자 유형별 제공범위를 다음과 같이 확정한다.

| 사용자 | 행사 전 | 행사 중 | 행사 후 |
| --- | --- | --- | --- |
| `GENERAL_REGISTERED` | 사전등록 연계(§9), 프로파일 확인(§9.3), 사전 추천 열람 | 개인화 홈(§11), 자연어 추가검색(§12), 관심목록(§13), 부스 위치 확인 | 알림함 후속정보(§8.2-11, W-6에서 상세화) - **본 MVP에서는 이메일·문자 발송 자체는 W-6 확정 전까지 범위 미정으로 둔다** |
| `BUYER_REGISTERED` | 위 항목 전부 + 바이어 프로파일 확인(§14.1) | 위 항목 전부 + 업체 매칭(§14.2)·간단 상담 요청(§16) | 상담 상태 확인(§16.2), 후속 정보 |
| `GUEST_WEB` | 없음(사전등록이 없으므로 "행사 전" 단계 자체가 없다) | 키오스크에서 넘어온 결과 열람(§23.3)만 - 자체 자연어 검색·개인화 추천은 **이번 MVP 범위에서 확정하지 않는다**(§6 미결정 사항 참고) | 없음(임시 세션이므로 행사 후 상태를 남기지 않는다) |

행사 전 단계가 없는 `GUEST_WEB`은 애초에 "사전등록"이 전제인 §9(사전등록 사용자 연계) 흐름을 타지 않는다 - 이는 마스터 스펙 §1의 서비스 정의("현장 비등록 방문객에게는 ... 자연어 검색을 통해 ... 제공")와 일치한다.

## 5. W-1 단계에서 확정하는 MVP 제외사항 (웹 모듈 한정)

마스터 스펙 §56 전체 제외목록 중 웹 초개인화 모듈에 직접 해당하는 항목만 다시 확인한다.

- 장기 거래 CRM, 견적·계약·정산, 샘플 배송, 발주관리, 거래처 관리(§15.2) - 바이어 매칭은 "추천→비교→상담 요청→수락/거절→연락처 공유"까지만(§15.1)이다.
- 복잡한 상담장 자동배정 - 상담은 요청·상태값 관리 수준(§16.2)만.
- 대규모 온라인 학습·복잡한 행동학습 - §34.1이 명시한 4가지 행동(관심 저장/상세조회/검색 클릭/명시적 제외)만 반영하고, "단일 클릭으로 장기 선호를 확정하지 않는다."
- 독립 마케팅 자동화 플랫폼 - 알림은 §8.2-11 "행사정보 알림" 수준.

## 6. 다음 단계(W-2)로 넘기기 전에 확정이 필요한 미결정 사항

W-1은 "무엇을 만들지"만 정하므로 다음은 의도적으로 미결정 상태로 남겨 W-2 이후에서 다룬다.

1. **`user_type` 값 이름**: 기존 스키마의 `GENERAL_VISITOR`/`BUYER`를 마스터 스펙의 `GENERAL_REGISTERED`/`BUYER_REGISTERED`로 실제 리네이밍할지, API 응답 레이어에서만 값을 매핑할지 - DB 마이그레이션 비용과 하위 호환성을 W-8(웹 API·DB)에서 비교한다.
2. **`GUEST_WEB`의 자체 검색·추천 범위**: QR로 넘어온 게스트가 웹에서 새 자연어 검색을 할 수 있는지, 아니면 키오스크 결과 열람만 가능한지 - 마스터 스펙 §23.3은 "업체 목록 보기·상세·지도"만 명시하고 "자연어 검색 가능"이라고 쓰지 않았다. W-3(화면 IA)에서 화면 유무로 확정한다.
3. ~~`DATA_REVIEWER`가 별도 role 코드로 이미 존재하는지~~ **[확인 완료]** `backend/alembic/versions/20260801_0002_0003_foundation.py`의 `role_code_allowed` CHECK 제약이 `role_code IN ('VISITOR', 'BUYER', 'EXHIBITOR', 'OPERATOR', 'ADMIN')`로 고정되어 있어 `DATA_REVIEWER`는 존재하지 않는다. 또한 마스터 스펙의 `EXHIBITOR_ADMIN`/`EVENT_ADMIN`도 기존 `EXHIBITOR`/`OPERATOR`·`ADMIN`과 이름이 정확히 일치하지 않는다. W-9(관리자 운영)에서 `role_code_allowed`를 `('VISITOR','BUYER','EXHIBITOR_ADMIN','EVENT_ADMIN','DATA_REVIEWER')` 방향으로 넓히는 마이그레이션이 필요한지, 혹은 API 레이어 매핑만으로 충분한지 결정한다 - §6-1 `user_type` 리네이밍 여부 결정과 동일한 성격의 문제이므로 두 결정을 W-8/W-9에서 함께 검토한다.
4. **행사 후 알림 채널(이메일·문자) 연동 범위**: 마스터 스펙 §8.2-11에는 있지만 §56 제외목록에 마케팅 자동화가 있어 경계가 모호하다 - W-6에서 "행사 후 1회성 정적 알림"과 "마케팅 자동화"의 경계선을 명시적으로 긋는다.

## 7. 이 문서가 바꾸지 않는 것

- `identity`/`profile`/`exhibition`/`matching`/`ontology` 스키마의 테이블 구조 자체는 이 문서 시점에는 변경하지 않는다. W-1은 순수 범위·분류 문서다.
- 기존에 구현된 매칭 서비스 계층(`backend/app/services/matching/*`, PR #3)은 그대로 유지한다. 재설계는 이 자산을 "웹 초개인화 모듈"의 W-5(개인화 추천 로직)/W-7(바이어 매칭) 단계에서 그대로 재사용하는 방향으로 진행한다(마스터 스펙 §57 "B2C 추천점수: 웹에 축소 적용", "B2B 점수: 바이어 매칭에 적용"과 일치).
