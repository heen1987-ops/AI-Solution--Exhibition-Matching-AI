# W-3. 웹 초개인화 모듈 - 사용자 화면 IA

근거 문서: `docs/redesign-v2/00-master-spec-v1.md`(§11~16), `docs/redesign-v2/01-module-split-plan.md`(§4-A W-3). [W-2](W-2-user-journey.md)의 여정 단계를 화면 단위로 쪼갠다. 화면 내부 레이아웃(버튼 배치 등)은 다루지 않고, "어떤 화면이 존재하는가"와 "어떤 사용자 유형이 그 화면에 접근 가능한가"만 확정한다.

## 1. 화면별 정의

### S-1. 개인화 홈

- 로그인 사용자 전용 진입점. 오늘의 추천 업체·부스 상위 N개 + 관심목록 바로가기 + (BUYER는) 바이어 매칭 바로가기.
- **GUEST_WEB이 접근 불가인 이유**: 개인화 홈은 "사용자를 알고 있는 상태"(01-module-split-plan.md §2.1)를 전제로 하는데, GUEST_WEB은 지속 프로파일이 없으므로 "개인화"할 대상 자체가 없다. GUEST_WEB의 대응 화면은 S-2(키오스크에서 넘어온 결과 목록)이다.

### S-2. 추천 업체·부스 목록

- GENERAL_REGISTERED/BUYER_REGISTERED: 프로파일 기반 개인화 추천 목록(W-5).
- GUEST_WEB: 키오스크 QR로 넘어온 검색 결과를 그대로 이어보는 목록 - **새로운 추천을 계산하지 않고 인계받은 결과를 표시만 한다**는 점이 GENERAL_REGISTERED와의 핵심 차이. [W-2 §3](W-2-user-journey.md)에서 "GUEST_WEB 자체 검색"을 미결정으로 남긴 것과 별개로, "인계받은 결과 열람"은 이 화면에서 항상 제공된다.

### S-3. 자연어 검색

- GENERAL_REGISTERED/BUYER_REGISTERED: 프로파일에 없는 "지금 이 순간의 추가 요구"를 자연어로 검색(§12). 검색 엔진 자체는 공통 플랫폼(C-4)을 공유하되, 결과 랭킹에 사용자 프로파일 신호를 추가 결합한다.
- GUEST_WEB: [W-2 §6-2](W-2-user-journey.md)의 미결정 사항 - 마스터 스펙 §23.3이 "목록 보기·상세·지도 보기"만 명시하고 자연어 검색을 언급하지 않으므로, **이 화면은 기본적으로 GUEST_WEB에 비활성화한다.** GUEST_WEB이 새로운 자연어 검색을 하고 싶다면 키오스크로 돌아가거나 회원 전환(S-8)을 거치는 것을 기본 흐름으로 확정한다. (확장 시 재검토 여지는 남기되, MVP 기본값은 "비활성".)

### S-4. 관심목록

- [W-2 §1-7](W-2-user-journey.md)에서 확인한 스키마 공백(`profile.saved_recommendable` 신설 필요)의 화면단 소비처.
- **GUEST_WEB 접근 불가**: [W-1 §3](W-1-scope-and-user-types.md)의 "지속 프로파일 없음" 원칙 - 저장은 본질적으로 지속 데이터이므로, 회원 전환 전에는 이 화면 자체를 노출하지 않는다. (브라우저 로컬 임시 저장은 §23.3에 명시된 대로 가능하지만, 이는 서버 측 "관심목록" 기능과는 별개이며 W-3 범위에서는 서버 기능만 다룬다.)

### S-5. 부스·업체 상세

- 3개 사용자 유형 모두 접근 가능한 유일한 화면 - 업체 상세 정보 자체는 로그인 여부와 무관하게 공개 데이터이기 때문(공통 플랫폼 C-1/C-6의 "업체 공개범위" 정책을 그대로 따름).
- GENERAL_REGISTERED/BUYER_REGISTERED에게는 이 화면에 "관심 저장" 버튼이 추가로 노출되고, GUEST_WEB에게는 노출되지 않는다(S-4와 동일한 원칙).

### S-6. 바이어 매칭

- BUYER_REGISTERED 전용. [W-2 §2](W-2-user-journey.md)의 "업체 매칭 추천 확인 → 비교 → 관심 저장 → 상담 요청" 흐름이 이 화면 하나에서 진행된다. 상담 요청 이후 상태 추적은 이 화면 내 하위 탭(상담 현황)으로 처리하고 별도 화면을 만들지 않는다 - §16.2의 "상담 상태 확인"이 마스터 스펙에서 별도 화면으로 요구되지 않기 때문.
- GENERAL_REGISTERED 접근 불가: 바이어 거래조건(`BuyerNeed`)이 없는 사용자에게는 매칭 대상 자체가 성립하지 않는다.

### S-7. MY 정보

- 프로파일 확인·수정(§9.3), 수신동의 관리(W-6과 연동), 계정 정보. GUEST_WEB은 계정이 없으므로 접근 불가 - 회원 전환 시 비로소 이 화면이 생긴다.

### S-8. 회원 전환

- GUEST_WEB 전용 화면. [W-2 §3](W-2-user-journey.md)의 "GUEST_WEB → 회원 전환 → 공통 여정 합류" 분기점. 전환 완료 시 S-1(개인화 홈)으로 리다이렉트되며, 이 시점부터 S-4/S-7 접근이 열린다.
- 전환 시 기존 게스트 데이터(방문세션·상황정보) 승계 범위는 [W-2 §4-1](W-2-user-journey.md)에서 이미 미결정 사항으로 남겨뒀다 - 이 화면의 실제 API 설계(W-8)에서 확정한다.

## 2. 화면과 공통 플랫폼(키오스크)의 경계

01-module-split-plan.md §2.3의 원칙("웹과 키오스크는 동일한 업체·부스 정보를 사용하지만 검색과 추천 방식은 분리")을 화면 단위로 다시 확인한다.

- S-5(부스·업체 상세)는 웹과 키오스크가 **콘텐츠를 공유**하지만 화면 자체는 각 모듈이 독립적으로 렌더링한다(키오스크는 큰 글자·터치 최적화가 필요 - K-6). 즉 "공유 데이터, 별도 화면"이지 "공유 화면"이 아니다.
- S-2/S-3은 웹 전용 로직(프로파일 결합)이 있어 키오스크의 대응 화면(K-3의 결과목록·검색화면)과 컴포넌트를 공유하지 않는다.

## 3. W-4로 넘기는 질문

W-3에서 "화면이 무엇을 보여줘야 하는지"가 정해졌으므로, W-4(프로파일 모델)에서는 각 화면이 실제로 읽고 쓰는 프로파일 필드를 확정한다. 특히:

1. S-7(MY 정보)에서 사용자가 직접 수정 가능한 필드와, 시스템이 자동 추론(`InferredPreference`)해 사용자에게는 읽기 전용으로만 보여주는 필드의 경계.
2. S-4(관심목록) 저장 시 `profile.saved_recommendable`(신설 테이블, [W-2 §1-7](W-2-user-journey.md))에 어떤 컨텍스트(저장 시점의 zone, 검색 키워드 등)를 함께 남길지.
