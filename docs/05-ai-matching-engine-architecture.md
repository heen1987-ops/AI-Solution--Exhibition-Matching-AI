## 1. 단계 결과

- 규칙·속성·임베딩·행동을 결합하는 하이브리드 구조를 채택한다.
- 일반 관람객과 바이어의 목적함수·정책을 분리한다.
- 생성형 AI는 자연어 구조화와 근거 기반 설명에만 사용한다.
- 후보검색, 하드 필터, 점수, 양면 적합도, 상황 재정렬, 다양성 보정을 독립 모듈로 둔다.
- 추천 당시 프로파일·택소노미·정책·모델·현장 스냅샷을 고정해 재현 가능하게 한다.
- 이 단계의 완료는 설계 산출물 완료이며 가중치 확정·구현·현장 검증은 후속 단계의 관문이다.

## 2. 단계 목적

본 단계의 목적은 사용자·바이어·참가업체·제품·부스·프로그램 데이터를 입력받아 적합 후보를 검색하고, 필수조건 검증·점수 계산·상황 재정렬·다양성 보정·추천 이유 생성을 수행하는 AI 매칭엔진의 전체 구조를 정의하는 데 있다.

본 단계에서는 세부 가중치와 개별 속성값을 확정하지 않는다. 대신 이후 단계에서 세분화할 수 있도록 매칭엔진의 책임과 경계를 고정한다.

## 3. 핵심 설계 판단

### 3.1 단일 AI 모델 방식 배제

전체 추천을 생성형 AI에 직접 질의하는 방식은 적용하지 않는다.

예시:

> "이 사용자의 정보를 보고 가장 적합한 업체를 추천해줘."

이 방식은 다음 문제가 있다.

* 동일 조건에도 결과가 달라질 가능성
* 필수 거래조건 누락 가능성
* 운영 종료·품절 정보 반영 불안정
* 추천순위 재현 곤란
* 추천근거 검증 곤란
* 프롬프트 변경에 따른 결과 변동
* 개인정보의 불필요한 외부 모델 전달 가능성

따라서 생성형 AI는 추천순위를 직접 결정하지 않고 자연어 해석과 추천 설명에 제한적으로 활용한다.

### 3.2 하이브리드 매칭엔진 적용

최종 매칭은 다음 네 가지 방식을 결합한다.

| 방식    | 적용 기능                           |
| ----- | ------------------------------- |
| 규칙 기반 | 연령, 운영상태, 가격, MOQ, 공급지역 등 필수조건  |
| 속성 기반 | 주종, 맛, 목적, 가격, 유통채널 등의 정형 속성 비교 |
| 의미 기반 | 사용자 자연어 요구와 업체·제품 설명 간 임베딩 유사도  |
| 행동 기반 | 조회, 저장, 제외, 방문, 상담, 만족도 데이터 반영  |

### 3.3 추천 유형별 모델 분리

일반 관람객 추천과 B2B 바이어 추천은 별도의 정책과 점수체계를 사용한다.

```text
일반 관람객
→ 제품·취향·시음·구매·체험 중심

바이어
→ 거래목적·유통채널·MOQ·가격·생산량·공급지역 중심
```

두 모델이 사용하는 데이터 일부는 공유하지만, 최종 목적함수는 분리한다.

## 5. 구성요소별 역할

### 5.1 Request Validator

추천 요청의 유효성을 검증한다.

#### 검증 항목

* 행사 운영 여부
* 사용자 세션 유효 여부
* 연령확인 여부
* 개인화 추천 동의 여부
* 사용자 유형 설정 여부
* 프로파일 최소 완성도
* 추천 유형 유효 여부
* 위치·시간 데이터 형식
* 요청량 제한

#### 출력

```json
{
  "request_valid": true,
  "user_type": "BUYER",
  "recommendation_type": "MIXED",
  "missing_fields": [],
  "policy_route": "BUYER_MATCHING_V1"
}
```

---

### 5.2 Profile Resolver

여러 위치에 저장된 사용자 데이터를 하나의 추천용 프로파일로 통합한다.

#### 입력 데이터

* 사용자가 직접 선택한 목적·취향
* 바이어 거래조건
* 과거 저장·조회·방문 행동
* 사용자 피드백
* AI가 추출한 자연어 요구조건
* 현재 적용 중인 프로파일 버전

#### 프로파일 우선순위

```text
사용자 직접 입력
> 사용자가 수정한 값
> 최근 명시적 피드백
> 반복 행동에서 추론한 값
> AI 자연어 추출값
> 기본값
```

AI가 추론한 값은 사용자가 직접 입력한 값을 덮어쓰지 않는다.

#### 출력 예시

```json
{
  "profile_id": "pf_001",
  "profile_version": 5,
  "user_type": "GENERAL_VISITOR",
  "goals": [
    {
      "code": "GIFT_SEARCH",
      "priority": 1,
      "source": "USER"
    }
  ],
  "preferences": {
    "categories": ["DISTILLED_LIQUOR"],
    "taste": ["DRY", "AROMATIC"],
    "price_max": 50000
  },
  "confidence": {
    "category": 1.0,
    "taste": 0.9,
    "price": 1.0
  }
}
```

---

### 5.3 Context Resolver

사용자의 현재 상황과 행사 운영상태를 결합한다.

#### 사용자 상황

* 현재 시간
* 남은 체류시간
* 현재 구역
* 이동 선호
* 이미 방문한 부스
* 확정된 상담일정
* 저장한 부스·제품
* 최근 제외한 추천

#### 행사 상황

* 부스 운영상태
* 제품 재고
* 시음·구매 가능 여부
* 부스 혼잡도
* 상담 가능시간
* 프로그램 시작시간
* 행사장 이동거리
* 긴급 운영공지

#### 출력

```json
{
  "current_zone": "ENTRANCE_A",
  "remaining_minutes": 65,
  "visited_booth_ids": ["booth_003"],
  "upcoming_meetings": [
    {
      "start_at": "2026-10-09T15:00:00+09:00",
      "booth_id": "booth_021"
    }
  ],
  "operational_snapshot_version": 42
}
```

### 5.4 Candidate Generator

추천 가능한 전체 참가업체·제품·부스·프로그램 중 상위 후보군을 빠르게 검색한다.

#### 후보 생성 채널

1. 구조화 속성 검색
2. 벡터 의미 검색
3. 인기·품질 기반 후보
4. 운영자 지정 후보
5. 사용자 관심목록 연관 후보
6. 탐색·신규성 후보

#### 후보군 병합 예시

```text
구조화 조건 후보       100개
벡터 유사도 후보        50개
인기·품질 후보          20개
신규업체 탐색 후보      10개
                      ─────
중복 제거 후 후보       120개
```

후보검색 단계에서는 최종순위를 결정하지 않는다. 충분한 재현율을 확보하는 것이 목적이다.

---

### 5.5 Hard Filter Engine

점수와 무관하게 추천이 불가능한 후보를 제거한다.

#### 공통 필수 필터

* 관리자 미승인
* 참가 취소
* 부스 운영 종료
* 행사일 불일치
* 제품 판매·시음 종료
* 사용자 명시적 제외
* 추천 대상 정보 부족

#### 일반 관람객 필터

* 가격 상한을 절대조건으로 설정한 경우 가격 초과
* 주류 추천 연령확인 미완료
* 접근성 필수조건 불일치
* 남은 시간 안에 방문 불가능

#### 바이어 필터

* 최소주문수량 불일치
* 공급지역 불일치
* 유통채널 불일치
* OEM·PB 필수조건 불일치
* 생산역량 부족
* 상담 가능시간 없음
* 수출 대상국 불일치

#### 처리 결과

각 제외 후보와 제외 사유를 저장한다.

```json
{
  "object_id": "ex_031",
  "passed": false,
  "filter_code": "MOQ_MISMATCH",
  "details": {
    "buyer_max": 100,
    "exhibitor_min": 500
  }
}
```

### 5.6 Feature Builder

후보와 사용자 간 비교에 사용할 매칭 특성을 생성한다.

#### 일반 관람객 특성

* 주종 일치도
* 맛 선호 일치도
* 도수 일치도
* 가격 일치도
* 시음·구매 가능성
* 선물·자가소비 적합도
* 이동거리
* 혼잡도
* 신규성
* 데이터 신뢰도

#### 바이어 특성

* 제품군 일치도
* 유통채널 일치도
* 가격 일치도
* MOQ 일치도
* 생산역량 적합도
* 공급지역 일치도
* OEM·PB 가능성
* 수출 가능성
* 상담주제 일치도
* 상담시간 일치도
* 업체 희망 바이어와의 상호 적합도

#### 출력 예시

```json
{
  "object_id": "product_001",
  "features": {
    "category_match": 1.0,
    "taste_match": 0.85,
    "price_match": 0.92,
    "goal_match": 0.88,
    "distance_score": 0.76,
    "congestion_score": 0.90,
    "data_trust": 0.95
  }
}
```

### 5.7 Base Scoring Engine

구조화된 특성을 바탕으로 기본 적합도를 계산한다.

#### 기본 구조

```text
기본점수 =
Σ(특성값 × 가중치)
```

#### 일반 관람객 기본점수

```text
취향 적합도
+ 방문목적 적합도
+ 가격·구매조건
+ 체험·프로그램 적합도
```

#### 바이어 기본점수

```text
거래목적 적합도
+ 제품군 적합도
+ 유통채널 적합도
+ 가격·MOQ 적합도
+ 공급지역·생산역량
+ 상담주제 적합도
```

정확한 가중치와 산식은 제11단계와 제12단계에서 확정한다.

### 5.8 Reciprocal Matching Engine

바이어가 업체를 원하는 정도와 업체가 해당 바이어를 원하는 정도를 함께 계산한다.

#### 방향별 점수

```text
Buyer → Exhibitor
바이어 요구조건과 업체 공급조건 일치도

Exhibitor → Buyer
업체 희망 바이어·채널·거래규모와 바이어 특성 일치도
```

#### 양면 적합도 기본 구조

```text
양면 적합도 =
Buyer→Exhibitor 점수 × α
+ Exhibitor→Buyer 점수 × β
```

한쪽 점수가 매우 낮은 경우 전체 점수에 감점 또는 상한을 적용한다.

예시:

```text
바이어 적합도 95점
업체 적합도 25점
→ 최종 60점대가 아니라 상한 50점 적용 가능
```

바이어는 매우 관심이 있지만 업체가 해당 채널에 공급할 계획이 없다면 높은 추천을 제공해서는 안 된다.

### 5.9 Context Re-ranker

기본 적합도에 행사 현장 상황을 반영하여 순위를 재조정한다.

#### 재정렬 요소

* 현재 위치와 거리
* 남은 체류시간
* 부스 대기시간
* 상담 가능시간
* 확정 일정과의 이동 가능성
* 제품 품절 임박
* 프로그램 시작시간
* 최근 방문·조회 이력
* 긴급 운영변경

#### 예시

```text
A업체 기본 적합도 92점
이동 15분, 대기 30분
남은 시간 25분
→ 순위 하락

B업체 기본 적합도 84점
이동 2분, 즉시 상담 가능
→ 현재 행동 추천 1순위
```

기본 적합도와 '지금 방문할 가치'는 분리해 저장한다.

### 5.10 Diversity & Policy Controller

상위 점수만 반복 노출되는 문제를 방지한다.

#### 다양성 보정

* 동일 주종 연속 추천 제한
* 동일 업체 다수 제품 중복 제한
* 지역·가격·제품군 다양성 확보
* 사용자가 아직 탐색하지 않은 분야 일부 제공
* 신규 참가업체 탐색 슬롯 제공

#### 운영정책

* 업체별 추천 노출 상한
* 스폰서 노출과 AI 추천 분리
* 행사 운영자 지정 제외
* 민원·품질 문제 업체 일시 제한
* 데이터 완성도 미달 업체 감점
* 특정 업체의 인위적 과다 노출 방지

#### 추천 슬롯 예시

```text
상위 적합도 추천        70%
상황 최적 추천          15%
탐색·다양성 추천        10%
신규업체 추천            5%
```

세부 비율은 운영 데이터에 따라 조정한다.

### 5.11 Explanation Generator

최종 추천 결과에 대해 사용자가 이해할 수 있는 추천 이유를 생성한다.

#### 추천 이유 생성 방식

1. 점수 기여도가 높은 특성 추출
2. 노출 가능한 근거인지 정책 검증
3. 템플릿 또는 LLM으로 문장 생성
4. 입력 사실과 문장 일치 검증
5. 사용자 화면에 최대 2~3개 표시

#### 예시

```text
- 선호한 드라이한 증류주 조건과 일치
- 희망 가격대에서 현장구매 가능
- 현재 위치에서 도보 3분
```

#### 금지 근거

* 성별·연령 기반 추정
* 사용자가 입력하지 않은 소비성향
* 업체가 제공하지 않은 품질·효능 주장
* 내부 점수·가중치
* 다른 사용자의 개인 데이터
* 광고비·스폰서 여부

## 6. 최종 매칭점수의 개념 구조

필수조건 통과 여부는 점수 항이 아니라 노출 자격이다. 먼저 Eligibility Gate를 평가하고, 통과한 후보에만 다음 점수를 계산한다.

```text
Eligibility Gate = false
→ 후보 제외, filter_result에 사유 저장

Eligibility Gate = true
→ 최종 추천점수 = clamp(
    기본 적합도
  + 양면 적합도
  + 행동 적합도
  + 상황 보정
  + 데이터 신뢰도
  + 다양성 보정
  - 운영 위험 감점,
  0, 100
)
```

### 구성요소

| 요소               | 의미             |
| ---------------- | -------------- |
| Eligibility Gate | 필수조건 통과 여부     |
| 기본 적합도           | 취향·목적·거래조건 일치  |
| 양면 적합도           | 바이어와 업체 상호 일치  |
| 행동 적합도           | 조회·저장·방문 패턴    |
| 상황 보정            | 거리·시간·혼잡·상담 가능 |
| 데이터 신뢰도          | 승인·완성도·최신성     |
| 다양성 보정           | 중복·편중 완화       |
| 운영 위험 감점         | 품절·민원·운영상태 불안정 |

Hard Filter를 통과하지 못한 대상에는 최종 점수와 순위를 부여하지 않는다. 진단이 필요한 경우 계산값은 운영 trace에만 저장하고 사용자 결과와 `match_result`에는 포함하지 않는다.

## 7. 추천 결과 유형

### 7.1 추천 결과 대상

| 대상   | 주요 사용 시점       |
| ---- | -------------- |
| 부스   | 현장 방문 추천       |
| 제품   | 취향·구매 추천       |
| 참가업체 | 바이어 거래처 발굴     |
| 프로그램 | 시음·세미나·체험 추천   |

`match_result`의 직접 대상은 `exhibition.recommendable`에 등록된 부스·행사제품·참가업체·프로그램이다. 상담과 경로는 추천 대상 자체가 아니라 추천 결과로부터 생성되는 후속 행동·산출물이며 각각 `interaction.meeting`, `interaction.route`에 저장한다.

### 7.2 추천 행동

```text
VISIT_NOW
SAVE_FOR_LATER
REQUEST_MEETING
ADD_TO_ROUTE
COMPARE_PRODUCTS
JOIN_PROGRAM
REFINE_PROFILE
```

추천 대상과 행동을 분리해야 한다.

예시:

* 제품 적합도가 높지만 부스가 혼잡한 경우: `SAVE_FOR_LATER`
* 업체 적합도가 높고 상담 가능시간이 있는 경우: `REQUEST_MEETING`
* 가까우며 대기시간이 짧은 경우: `VISIT_NOW`

## 9. 추천 유효상태와 행동 이벤트

```text
ACTIVE
├─→ EXPIRED
└─→ INVALIDATED
```

### 9.1 추천 세션 유효상태

| 상태         | 설명              |
| ---------- | --------------- |
| ACTIVE     | 사용자에게 제공 가능     |
| EXPIRED    | 유효시간 만료 또는 시간성 현장조건 소멸 |
| INVALIDATED | 프로파일·정책·대상 상태 변경으로 결과 폐기 |

추천 결과와 항목은 하나의 선형 참여 상태를 갖지 않는다. 노출·조회·저장·경로추가·방문·상담·전환은 동시에 여러 번 발생할 수 있으므로 `interaction.interaction_event`에 append-only 이벤트로 기록한다.

### 9.2 즉시 무효화 조건

* 사용자 프로파일 변경
* 부스 운영 종료
* 제품 품절
* 상담 슬롯 예약 완료
* 남은 체류시간 급변
* 추천정책 버전 변경
* 사용자의 명시적 제외

TTL 경과는 `EXPIRED`, 프로파일·정책·추천대상 변경은 `INVALIDATED`로 구분한다. 단일 항목만 무효가 된 경우 세션 전체를 폐기할지 해당 항목만 숨길지는 정책으로 결정하고 사유코드를 남긴다.

* 구조화 속성 검색만으로 후보 생성
* 최근 인기·품질 후보 보조
* 장애 이벤트 기록

### 10.3 실시간 부스정보 미수신

* 마지막 정상 상태 사용
* 데이터 기준시점 표시
* 일정시간 이상 미갱신 시 상황점수 제외

* 최소 질문 추가 제시


```text
POST /api/v1/recommendations
```

### 12.2 MVP 내부 모듈

```text
RecommendationOrchestrator.generate(command)

HardFilterEngine.evaluate(candidates, context)
```

초기 MVP에서는 위 경계를 동일 배포 단위의 typed interface로 구현한다. 내부 호출을 공개 HTTP API로 만들지 않는다.

- 모듈별 독립 확장 필요성이 부하 시험으로 확인됨

- 네트워크 지연과 장애 전파 비용보다 분리 이익이 큼
- 관측성·재시도·멱등성·계약 테스트를 갖춤

분리 후에도 외부 클라이언트는 공개 추천 API만 호출한다.
