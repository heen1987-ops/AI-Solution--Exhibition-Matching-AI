## 1. 결론

이번 행사에는 기존 홈페이지와 관리자 시스템을 전면 개편하지 않고, 별도 모바일 웹과 매칭 DB를 구축해 연결하는 **독립형 연계 MVP(A+)**가 적합하다.

- 기존 `backju.kr`는 행사·사전등록·참가신청 데이터의 원천 시스템으로 유지한다.
- 백주 AI 셀파는 사용자 프로파일, 제품·거래조건, 행동 이벤트, 추천, 상담 일정을 별도 관리한다.
- 초기 데이터 연계는 CSV 또는 읽기 전용 API로 시작하고, 즉시성이 꼭 필요한 지점만 서명 토큰·웹훅으로 연동한다.
- 일반 관람객 추천과 바이어 B2B 매칭은 입력정보와 성공 기준이 다르므로 별도 점수 모델로 운영한다.
- LLM은 대화, 자연어 조건 구조화, 설명 생성에 사용하고 최종 필터·점수·노출은 통제 가능한 규칙과 구조화 데이터로 결정한다.

서비스가 답해야 하는 핵심 질문은 “어떤 부스가 인기 있는가”가 아니라 다음과 같다.

> 지금 이 방문객 또는 바이어에게 가장 가치 있는 만남은 무엇이며, 왜 지금 만나야 하는가?

### 2.2 관람객 사전등록 실제 필드

사전등록 폼은 `POST /theme/theme_2/join_member_update_enc.php`로 제출된다. 기존 제출 동작을 우회하거나 클라이언트에서 복제하지 않고, 원천 시스템에서 저장이 성공한 뒤 export 또는 서버 간 웹훅으로 전달해야 한다.

| 원본 필드 | 의미 | 표준 필드 | 매칭 사용 |
|---|---|---|---|
| `mb_name` | 성명 | `identity.name` | 식별 전용 |
| `mb_gender` | 성별 | `identity.gender` | 추천 점수에서 제외 |
| `mb_tel1~3` | 휴대전화 | `identity.phone` | 본인 연결·연락 동의 |
| `mb_email1~2` | 이메일 | `identity.email` | 본인 연결·연락 동의 |
| `poll1` | 거주지역 | `profile.home_region` | 약한 보조 신호 |
| `mb_age` | 연령대 | `profile.age_band` | 추천 점수에서 제외 |
| `poll4[]` | 관심분야 6종 | `profile.interest_categories[]` | 1차 후보 생성 |
| `poll3[]` | 관람목적 4종 | `profile.visit_goals[]` | 1차 후보 생성 |
| `poll5[]` | 인지경로 | `attribution.channels[]` | 마케팅 분석, 추천 제외 |
| `agree1` | 개인정보 수집 동의 | `consent.registration` | 원천 등록 근거 |
| `agree3` | 행사안내 수신 선택동의 | `consent.marketing` | 발송 채널 통제 |

- 일반 관람객: 주종 세분, 단맛·산미·향·바디·도수, 예산, 구매수량, 선물/자가소비, 체류시간, 체험 선호
- 바이어: 소속·업종, 유통채널, 목표 가격, MOQ, 공급지역, OEM/PB/독점유통 관심, 의사결정 시점
- 현장 맥락: 현재 구역, 대기시간, 시음·제품 재고, 상담 가능시간

### 2.3 참가업체 신청 실제 필드

참가업체 폼은 `POST /theme/theme_2/join_company_update.php`로 제출된다.

| 원본 필드 | 현재 수집정보 | 표준 매핑 |
|---|---|---|
| `field1~10` | 탁주, 약주, 청주, 증류주, 기타주류, 음식, 라이프스타일, 양조기술, 지역문화, 주류 B2B | `exhibitor.categories[]` |
| `company_name` | 회사명 | `exhibitor.legal_name` |
| `sign_kr` | 상호간판명 | `exhibitor.display_name` |
| `company_addr` | 주소 | `exhibitor.region` |
| `website` | 홈페이지 | `exhibitor.website_url` |
| `manager_name`, 연락처, 이메일 | 담당자 정보 | 식별정보 저장소의 `exhibitor_contact` |
| `product_kr` | 전시품목 | `product.raw_description` |
| `main_img`, `product_img*` | 대표·제품 사진 | `media_asset` |
| `etc_text` | 양조장 이야기 | `exhibitor.story` |
| `field25` | 관람객 대상 현장 프로모션 | `booth.promotion_description` |
| `field24` | 행사·콜라보 협찬 여부 | 운영 메타데이터 |
| `booth1~3` 등 | 부스·유틸리티 신청 | 운영·정산 데이터, 매칭 입력에서 제외 |

기존 참가신청은 단순 회사명·품목을 넘어 소개문, 이미지, 현장 프로모션까지 수집한다. 따라서 이 데이터는 업체 카드와 의미검색의 좋은 출발점이다. 다만 다음 항목은 별도 보강 폼이 필요하다.

- 제품 단위: 제품명, 주종, 원료, 맛·향, 도수, 용량, 소비자가, 현장구매·택배 가능 여부, 시음 여부
- B2B: 출고가, MOQ, 월 생산량, 공급지역, 유통채널, 인증, OEM/PB/독점 조건
- 상담: 담당자, 상담주제, 가능한 시간, 동시 수용 인원
- 운영: 부스번호·좌표, 영업 상태, 품절·시음 마감, 예상 대기시간
- 희망 상대: 소비자 유형, 바이어 업종·채널·지역·규모

### 2.4 개인정보 문구 불일치

사전등록 화면에는 홈페이지 개발·유지보수 업체가 `라온비앤피`로 표시되고 마케팅 활용기간을 5년으로 안내한다. 별도 개인정보 취급방침에는 수탁기관이 `㈜더페어스`로 표시되고 처리 목적 달성 후 파기를 원칙으로 설명한다.

이는 신규 매칭서비스가 데이터를 받기 전에 실제 개인정보처리자, 수탁자, 처리 목적, 항목, 보유기간, 파기 절차를 하나의 최신 문서로 일치시켜야 한다는 뜻이다. 본 문서는 법률 자문을 대체하지 않으며, 실제 동의문과 처리방침은 개인정보 담당자와 법률 검토를 거쳐 확정한다.

## 3. 서비스 범위

### 3.1 사용자 유형

- 일반 관람객 ↔ 제품·양조장·시음·체험 프로그램
- 바이어 ↔ 참가업체·제품·거래조건·상담 담당자
- 참가업체 ↔ 동의한 잠재고객·바이어·상담 요청
- 운영자 ↔ 정보 완성도·혼잡도·상담성과·수요 분석

### 3.2 개인화 5단계

1. **Profile**: 취향, 방문 목적, 구매·거래 조건을 구조화한다.
2. **Goal**: “5만 원 이하 선물”, “수도권 바틀샵 납품처 발굴”처럼 이번 방문의 달성 목표를 반영한다.
3. **Context**: 현재 시간, 남은 체류시간, QR로 확인한 구역, 이동거리, 대기시간, 재고, 상담 가능성을 반영한다.
4. **Reciprocal**: 바이어가 업체에 적합한지와 업체가 원하는 바이어인지 양방향으로 평가한다.
5. **Adaptive**: 저장, 제외, 상세조회, QR 체크인, 상담, 평가에 따라 추천을 갱신한다.

초기 현장 위치는 정밀 실내측위 대신 입구·구역·부스 QR 체크인으로 수집한다.

### 4.1 권장 기술 구성

| 영역 | MVP 권장안 |
|---|---|
| 사용자·업체·관리자 웹 | 반응형 웹/PWA |
| API | FastAPI 또는 NestJS 중 팀 역량에 맞춰 단일 선택 |
| 관계형 DB | PostgreSQL |
| 의미검색 | pgvector, V1부터 적용 |
| 비동기 처리 | 관리형 큐 또는 Redis 기반 작업 큐 |
| 이미지 | 접근통제 가능한 오브젝트 스토리지 |
| 인증 | 운영자 RBAC, 사용자 서명 링크 또는 OTP |
| 관측성 | 구조화 로그, 오류 추적, 감사로그, 지표 |
| 배포 | 독립 도메인·서브도메인, 기존 사이트와 느슨한 결합 |

모든 업무 데이터에는 `tenant_id`와 `event_id`를 함께 둔다. `event_id`만으로는 여러 주최사를 안전하게 격리하는 멀티테넌시가 완성되지 않는다.

```text
              │ 가명 user_id
              ▼
[매칭 프로파일 DB]
취향 · 목적 · 거래조건 · 행동 · 상담상태
              │
              ▼
[매칭 엔진]
후보 · 점수 · 추천사유 · 다음 행동
```

- 일반 매칭 처리에는 연락처 원문을 전달하지 않는다.
- 참가업체 담당자 정보도 개인을 식별할 수 있으므로 개인정보로 취급한다.
- 전화번호·이메일 매칭용 값은 단순 SHA-256이 아니라 서버 비밀키 기반 HMAC을 사용한다.
- 원천 사이트가 알림을 발송할 수 있다면 셀파는 연락처 원문 대신 불투명한 원천 식별자와 아웃바운드 웹훅을 사용한다.
- 성별·연령대는 추천 점수에 직접 쓰지 않는다. 만 19세 이상 여부는 서비스 적격성에만 사용한다.

## 6. AI 및 매칭 엔진

### 6.1 역할 분리

LLM이 수행하는 일:

- 60초 대화형 추가 질문
- 자연어 방문 목표를 구조화 조건으로 변환
- 자유서술 업체·제품 소개에서 후보 속성 추출
- 사용자가 수정할 수 있는 추천 이유 생성

규칙·랭킹 엔진이 수행하는 일:

- 필수조건 필터
- 구조화 속성 점수
- 의미 유사도
- 시간·거리·혼잡 기반 재정렬
- 다양성·노출 편중 통제
- 모델·규칙 버전과 점수 근거 저장

LLM은 임의 업체를 생성하지 못하도록 서버가 제공한 후보 ID만 반환한다. 최종 점수와 노출 여부는 서버에서 검증하며, 추천 사유에 실제 데이터에 없는 가격·재고·혜택을 넣지 못하도록 근거 필드를 함께 검증한다.

### 6.2 일반 관람객 초기 가중치

```text
제품·취향 적합도       30%
방문목적 적합도        20%
가격·구매조건 적합도   15%
시간·거리·혼잡도       15%
행동기반 관심도        10%
신규성·다양성           5%
정보 신뢰도             5%
```

### 6.3 바이어 초기 가중치

```text
거래목적 적합도        25%
제품·카테고리 적합도   20%
유통채널 적합도        15%
가격·MOQ 적합도        15%

상담 가능시간           5%
정보 신뢰도             5%
```

초기 가중치는 가설이다. 전문가 평가와 행사 행동·상담 결과를 기준으로 조정하며 사용자 집단별 성과를 함께 점검한다.

2. 공통 택소노미 기반 구조화 후보 생성
3. 설명·상담요약 임베딩 유사도 후보 보강
4. 사용자 유형별 점수 계산
5. 시간·거리·혼잡·상담 가능성 재정렬
6. 동일 주종 반복, 업체별 과다 노출, 스폰서 혼입 방지
7. 근거 필드 기반 추천 이유 생성

### 6.6 다양성·신뢰 제어

- 동일 주종 연속 추천 제한
- 신규·소규모 업체 탐색 슬롯

- 정보가 부족한 업체는 높은 점수를 만들지 않고 `정보 보강 필요`로 표시

## 8. 연동 계약

### 8.1 1차 연동

- 참가업체와 관람객 CSV는 원본 파일, import 실행, 행별 결과를 보관한다.
- import는 `source_record_id`와 `source_updated_at`으로 멱등 upsert한다.
- 잘못된 행은 전체 배치를 중단하지 않고 오류 격리 목록으로 보낸다.
- 매핑표는 코드에 하드코딩하지 않고 이벤트별 버전으로 관리한다.

### 8.2 실시간 연동

- 웹훅에는 이벤트 ID, 이벤트 유형, 원천 레코드 ID, 변경시각, 페이로드 버전을 포함한다.
- HMAC 서명, 타임스탬프 허용범위, 재전송 방지 ID, 지수 백오프 재시도를 적용한다.
- 사용자 페이지에 `visitorRef`를 그대로 노출하지 않는다. 짧은 만료시간의 1회용 서명 토큰으로 프로파일을 연결한다.
- 위젯 또는 모바일웹 API는 이벤트·사용자·허용 작업이 제한된 토큰만 받는다.

### 8.3 주요 API 경계

```text
POST /v1/events/{eventId}/imports/visitors
POST /v1/events/{eventId}/imports/exhibitors
POST /v1/events/{eventId}/imports/products
POST /v1/profile-sessions
POST /v1/profile-sessions/{id}/answers
GET  /v1/recommendations
POST /v1/interactions
POST /v1/meeting-requests
POST /v1/meeting-requests/{id}/decision
POST /v1/webhooks/backju
```

API 키는 평문 저장하지 않고 해시 보관하며, 테넌트·이벤트·작업 범위와 만료일을 부여한다.

## 9. 개인정보·보안·운영 신뢰

필수 조치:

- 사전등록, 개인화 프로파일링, 현장 행동수집, 마케팅 수신, 참가업체 연락처 공유의 목적과 동의를 분리
- 개인화 기능 미동의자에게도 기본 행사정보와 일반 탐색 제공
- 사용자가 상담 요청 또는 연락처 공유를 승인한 시점에만 업체로 개인정보 전달
- 추천에 사용한 주요 조건과 추천 이유 제공
- 개인화 중지, 프로파일 초기화, 열람·정정·삭제·철회 기능 제공
- 역할별 최소권한, 운영자 MFA, 개인정보 다운로드 통제, 관리자·서비스 접근로그 적용
- 원본 import 파일과 이미지에 접근통제·악성파일 검사·보유기간 적용
- 운영 DB 백업, 복구훈련, 장애 대응 연락망, 행사장 네트워크 불안정 대비 캐시 적용

추천이 단순 선택 지원을 넘어 바이어 노출, 상담기회 또는 업체 배정을 자동 확정한다면 영향이 커진다. 그 경우 기준·사용정보·처리과정·권리행사 방법을 공개하고, 이의제기와 운영자 검토 절차를 제공한다.

- 목적별 동의·철회·삭제 처리

### 10.2 1차 제외

- 실시간 정밀 실내측위

### 10.3 단계적 AI 적용

- **MVP**: 구조화 조건과 규칙 점수 중심, LLM은 대화·속성 추출·설명에만 사용
- **V1**: 검수된 업체·제품 설명 임베딩과 상담요약 유사도 추가
- **V2**: 충분한 방문·상담 결과가 쌓인 뒤 가중치 학습과 실험 체계 도입

## 13. 구현 착수 전 의사결정

다음 항목은 1주차 안에 확정해야 한다.

1. 관리자 계정 또는 기존 개발사를 통한 실제 DB/CSV 샘플 확보
2. 원천 사이트가 실시간 웹훅을 추가할 수 있는지, 아니면 배치 export만 가능한지
3. AI 상담이 기존 시스템에 있는지와 세션 ID·사용자 ID 연결 방식
4. 참가업체·제품·부스배치 데이터의 승인 책임자
5. SMS·카카오알림톡 발송 주체와 연락처 원문 보관 주체
6. 참가업체에 방문객 연락처가 공개되는 정확한 동의 시점
7. 행사장 네트워크, QR 인쇄·부착, 운영요원 업무분장
8. 기존 개인정보 문서의 수탁자·보유기간 불일치 정비

## 14. 최종 권고

백주 AI 셀파의 경쟁력은 챗봇 자체가 아니라 다음 세 가지에서 나온다.

1. 관람객 수요와 참가업체 공급조건을 동일한 택소노미로 구조화하는 데이터 설계
2. 취향·거래조건·시간·거리·상담 가능성을 반영하는 설명 가능한 양면 매칭
3. 추천 → 방문 → 상담 → 후속조치로 이어지는 측정 가능한 피드백 구조

2026년에는 독립형 모바일 웹 MVP로 가설을 검증하고, 행사 종료 후 실제 방문·상담 데이터를 근거로 기존 홈페이지와의 정식 통합 범위를 결정한다.
