# AI 초개인화 매칭 서비스 — 아키텍처 설계

> **문서 상태:** 초기 아키텍처 초안. 사이트 실사와 실행계획을 반영한 최신 기준 문서는 [2026 대한민국 백주대간 초개인화 AI 매칭서비스 통합 설계안](./2026-backju-ai-matching-service-design.md)이다.
> 사용자 화면과 상태·분석 이벤트 기준은 [사용자 화면 IA·와이어프레임](./user-ia-wireframes.md)을 따른다.

## 0. 배경 및 범위

- 대상 유스케이스: `backju.kr`(2026 대한민국 백주대간) 같은 전시회 사이트에서, **사전등록 방문객 ↔ 참가기업(부스)** 을 AI로 매칭.
- 포지셔닝: 전시회 사이트(backju.kr)를 직접 개조하지 않고, **별도의 모듈형 매칭 플랫폼("Meet AI Match")** 으로 구축해 여러 전시회 사이트에 API/위젯 형태로 꽂아 쓸 수 있게 한다.
- 산출물 범위: 이 문서는 구현 이전 단계의 **아키텍처 설계**다. 코드는 없음.

## 1. 시스템 포지셔닝

```
┌─────────────────────┐        연동(API/Webhook/Embed)        ┌─────────────────────────┐
│   전시회 사이트 A     │ ───────────────────────────────────▶ │                          │
│   backju.kr          │ ◀─────────────────────────────────── │   Meet AI Match 플랫폼   │
│  (사전등록 폼, 부스DB, │        매칭결과/추천 위젯 응답          │   (독립 서비스)          │
│   AI상담 챗봇)         │                                      │                          │
└─────────────────────┘                                        └─────────────────────────┘
┌─────────────────────┐
│   전시회 사이트 B     │ ───────────────────────────────────▶  (동일한 방식으로 연동)
└─────────────────────┘
```

핵심 원칙: 각 전시회 사이트는 **자기 데이터의 출처(source of truth)** 로 남고, Meet AI Match는 그 데이터를 이벤트 단위(`event_id`)로 수집·정규화해 매칭만 전담한다. 사이트마다 폼 필드명이 달라도 표준 스키마로 매핑해 흡수한다.

## 2. 데이터 모델

세 가지 데이터 소스(사전등록 설문, 참가기업 정보, AI상담 대화 로그)를 표준 스키마로 정규화한다.

### 2.1 방문객 (Visitor / 사전등록자)

`backju.kr`의 실제 사전등록 폼(`sub.php?code=03_0302`) 항목을 기준으로 표준화:

```
visitor
├─ id                  (uuid, PK)
├─ event_id            (FK → event)
├─ source_site         ("backju.kr" 등, 연동 사이트 식별)
├─ external_ref         (원본 사이트의 사용자 식별자, 있는 경우)
├─ name
├─ gender
├─ phone                (해시 저장 권장, 아래 §6 참고)
├─ email                (해시 저장 권장)
├─ region               (거주지역: 서울·경기·인천 / 대구·경북 / ... )
├─ age_group            (20대/30대/.../60대 이상)
├─ interests[]          (관심분야, 다중: 우리술/기타주류/연관제품/기술/가맹/지역문화)
├─ visit_purpose[]      (관람목적, 다중: 구매/시음·이벤트/비즈니스/기타)
├─ referral_channel     (인지경로)
├─ marketing_consent    (bool, 마케팅 수신동의)
├─ age_verified         (bool, 19세 이상 동의)
├─ registered_at
└─ consent_expires_at   (동의 보유기간 만료일 — 기존 정책상 5년)
```

### 2.2 참가기업 / 부스 (Exhibitor)

```
exhibitor
├─ id                   (uuid, PK)
├─ event_id
├─ company_name
├─ booth_no
├─ industry_category     (업종 대분류)
├─ product_tags[]        (취급 주종/제품 태그 — 방문객 interests[]와 동일 택소노미 사용)
├─ description            (부스/기업 소개 텍스트 → 임베딩 대상)
├─ target_visitor_purpose[] (이 부스가 응대 가능한 관람목적: 구매/시음/비즈니스 등)
├─ contact_person, contact_phone, contact_email
├─ available_slots[]      (상담 가능 시간대 — 오프라인 미팅 매칭 시 필요)
└─ status                 (등록/승인/취소)
```

### 2.3 AI상담 대화 로그

```
consult_session
├─ id
├─ event_id
├─ visitor_id            (FK, null 가능 — 비회원 상담)
├─ started_at / ended_at
├─ messages[]             (role, text, timestamp)
├─ extracted_intents[]    (LLM 추출: 관심 주종, 예산, 방문 목적, 언급된 기업명 등)
└─ summary_embedding      (대화 요약의 벡터, 매칭 엔진 입력)
```

### 2.4 매칭 결과 / 피드백

```
match_result
├─ id
├─ event_id
├─ visitor_id
├─ exhibitor_id
├─ score                  (0~1, 최종 랭킹 점수)
├─ reason                 (LLM이 생성한 추천 이유 — 개인화 문구)
├─ delivered_via           (위젯/이메일/SMS/카카오알림톡/AI상담 챗봇)
├─ delivered_at
└─ feedback                (클릭/부스방문/무시 — 재학습용 신호)
```

## 3. 백엔드 아키텍처

```
                ┌───────────────────────────────────────────────┐
                │                Ingestion Layer                 │
                │  - Form Webhook Adapter (사전등록 폼)           │
                │  - Exhibitor Sync Adapter (부스 관리 CMS/엑셀)   │
                │  - Chat Log Adapter (AI상담 챗봇 이벤트 스트림)   │
                └───────────────────────────────────────────────┘
                                     │  정규화 → 표준 스키마
                                     ▼
                ┌───────────────────────────────────────────────┐
                │            정규화 데이터 저장소                 │
                │  - RDB(Postgres): visitor / exhibitor / event  │
                │  - Vector DB: 설명·대화 요약 임베딩              │
                └───────────────────────────────────────────────┘
                                     │
                                     ▼
                ┌───────────────────────────────────────────────┐
                │                 매칭 엔진                       │
                │  1) 규칙 필터 (연령/지역/관람목적 하드 조건)      │
                │  2) 임베딩 유사도 후보 생성 (top-K)              │
                │  3) LLM 재랭킹 + 추천 사유 생성                  │
                └───────────────────────────────────────────────┘
                                     │
                                     ▼
                ┌───────────────────────────────────────────────┐
                │                  API 계층                       │
                │  - REST: /v1/events/{id}/visitors/{id}/matches │
                │  - Webhook: 매칭 완료 시 사이트로 push           │
                │  - Embed SDK: 위젯 스니펫(iframe/JS)             │
                └───────────────────────────────────────────────┘
                                     │
                                     ▼
                ┌───────────────────────────────────────────────┐
                │           운영자(주최측) 관리 대시보드            │
                │  - 부스/방문객 데이터 현황, 매칭 결과 모니터링    │
                │  - 매칭 가중치(관심분야/지역/AI상담 비중) 조정    │
                └───────────────────────────────────────────────┘
```

## 4. 사이트/모듈 구조 (연동 방식)

전시회 사이트(backju.kr 등)에는 코드 변경을 최소화하고 아래 3가지 연동 지점만 추가:

1. **사전등록 폼 제출 시 Webhook** — 기존 `sub.php` 제출 로직에 매칭 플랫폼으로의 비동기 POST 1건 추가 (또는 DB 변경분 폴링 동기화로 대체 가능, 사이트 소스코드 접근 권한에 따라 선택).
2. **추천 위젯 임베드** — 방문객이 등록 완료 후 "관심 있을 만한 부스" 카드형 위젯을 `<script>` 스니펫으로 삽입 (마이페이지/등록완료 페이지).
3. **AI상담 챗봇 연동** — 기존 AI상담 챗봇의 대화 이벤트를 Meet AI Match로 스트리밍(또는 세션 종료 시 배치 전송)해 관심 신호로 활용, 챗봇 응답에 매칭된 부스 추천을 자연어로 삽입.

## 5. AI 매칭 파이프라인

1. **수집/정규화**: 사전등록 폼, 부스DB, 상담 로그를 §2 스키마로 표준화. 관심분야·제품태그는 공통 택소노미로 매핑.
2. **특징 추출**:
   - 규칙 기반: interests[], visit_purpose[], region, age_group → exhibitor의 product_tags[]/target_visitor_purpose[] 대응.
   - 임베딩 기반: exhibitor.description, consult_session.summary_embedding을 같은 임베딩 공간에 투영.
3. **후보 생성**: 방문객 벡터 기준 exhibitor 임베딩 top-K 유사도 검색(vector DB) + 규칙 필터로 1차 후보군 축소.
4. **재랭킹**: LLM이 방문객 프로필 + AI상담 요약 + 후보 부스 설명을 함께 보고 최종 점수·순위 산정, 어뷰징 방지를 위해 사이트 성격상 **19세 이상 동의** 등 하드 제약은 재랭킹 이전에 강제 필터로 걸러야 함.
5. **추천 사유 생성**: LLM이 "왜 이 부스를 추천하는지" 1~2문장 개인화 문구 생성 (예: "시음·이벤트 참여를 원하시고 증류주에 관심 있다고 하셔서 OO양조장 부스를 추천드려요").
6. **전달**: 위젯/이메일/SMS/카카오알림톡/AI상담 챗봇 중 방문객의 `marketing_consent` 채널에 맞게 전달.
7. **피드백 수집**: 클릭·부스 방문(QR 체크인 등) 신호를 `match_result.feedback`에 기록 → 가중치 튜닝 및 향후 재랭킹 모델 개선에 사용.

## 6. 개인정보 / 컴플라이언스

`backju.kr` 개인정보처리방침과 정합성을 맞춰야 함:

- 사전등록 화면의 5년 표기는 전시회 광고·마케팅 활용기간이다. 별도 개인정보 취급방침은 목적 달성 후 파기를 원칙으로 두고 있으므로, 데이터 목적별 보유기간을 다시 확정하고 각각의 `retention_expires_at` 기준으로 자동 파기해야 한다.
- 마케팅 수신 동의 여부에 따라 전달 채널 제한 (`marketing_consent = false`면 위젯 노출만, 이메일/SMS/알림톡 발송 금지).
- 만 19세 미만 방문객은 매칭 대상에서 제외 (`age_verified` 필수 필터).
- 전화번호/이메일은 원본 사이트가 보유하는 것이 원칙이며, Meet AI Match 측에는 매칭에 필요한 최소 항목만 해시 또는 가명처리해 저장 (직접 마케팅 발송이 필요한 경우만 원문 보관, 별도 위탁계약 필요 — 기존 위탁처리 조항에 "Meet AI Match" 추가 필요).
- 회사·제품·부스의 공개 정보와 담당자 성명·연락처를 분리해야 한다. 전자는 업체정보지만 담당자 정보는 개인정보이므로 목적·권한·보유기간 통제를 동일하게 적용한다.

## 7. 기술 스택 제안 (초안)

| 영역 | 제안 |
|---|---|
| 백엔드 API | Node.js(NestJS) 또는 Python(FastAPI) |
| RDB | PostgreSQL |
| 벡터 검색 | pgvector(PostgreSQL 확장) — 초기 규모에서 별도 벡터DB 불필요 |
| 임베딩/재랭킹 LLM | Claude API (임베딩은 별도 임베딩 모델 + Claude로 재랭킹/사유생성) |
| 연동 | Webhook + 경량 Embed JS SDK |
| 대시보드 | 기존 CMS와 분리된 별도 관리자 웹앱 |

## 8. 단계별 로드맵

- **MVP**: 단일 이벤트(backju.kr) 대상, 규칙 기반 매칭(임베딩 없이 interests[]/product_tags[] 교집합 점수)만으로 위젯 노출. AI상담 로그는 아직 미연동.
- **V1**: 임베딩 기반 유사도 + LLM 재랭킹·추천사유 생성 추가. AI상담 대화 로그를 매칭 신호로 편입.
- **V2**: 다중 이벤트/사이트 지원(멀티테넌시), 운영자 대시보드에서 가중치 조정 UI, 피드백 기반 자동 튜닝.

## 10. 미해결 질문 (다음 논의 필요)

- `/adm/`은 관리자 로그인으로 연결되는 것을 확인했다. 관리자 계정 또는 기존 개발사 협조를 통해 실제 DB/CSV export 샘플과 부스번호·배치도 제공 형식을 확인해야 한다.
- 공개 참가신청 폼에는 전시분야, 전시품목, 양조장 소개, 대표·제품 사진, 현장 프로모션이 이미 수집된다. 제품별 가격·맛·도수·MOQ·공급지역·상담시간 등 매칭용 보강 항목의 입력 주체와 승인 절차를 확정해야 한다.
- AI상담 챗봇이 현재 어떤 플랫폼(자체 구축/서드파티)으로 운영 중인지에 따라 §4의 연동 방식(스트리밍 vs 배치)이 달라짐.
- 전화번호/이메일 해시 저장 시 매칭 알림 발송(SMS/카카오알림톡)을 Meet AI Match가 직접 할지, 원본 사이트가 발송을 대행할지 결정 필요.
