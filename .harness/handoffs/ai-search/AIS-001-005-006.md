## 완료 내용

### AIS-001 - Gold Set 구조 + 초기 샘플

`ai/evaluation/{queries,expected,schemas}/` 구조를 만들고 총 15건의 질의 샘플을 채웠다:

- `queries/guest-web-ko.jsonl` - 5건(채널=GUEST_WEB, profile_context=NONE). 디스패치가 예시로 든
  5개 질의(AI 기술 보유/친환경 포장재/다국어 안내 솔루션/물류 자동화 로봇/스마트공장 설비)를
  그대로 썼다.
- `queries/consumer-ko.jsonl` - 3건(채널=WEB, profile_context 있음: CONSUMER_BUYER/
  GENERAL_VISITOR). AIS-002가 이미 실측 확인한 ko-KR 동의어 3쌍(막걸리→ALCOHOL.TAKJU,
  목 넘김이 좋은→TASTE.SMOOTH, 독하지 않은→TASTE.MILD, 달지 않은→TASTE.DRY, 전통 소주→
  ALCOHOL.SOJU_DISTILLED)을 그대로 재사용해 안전하게 구성했다.
- `queries/buyer-ko.jsonl` - 4건(채널=WEB, profile_context=BUSINESS_BUYER). 디스패치 예시
  4개(OEM 가능 식품/온라인 유통 가능/일본 수출 경험/초기 소량 공급)를 그대로 썼다.
- `queries/multilingual.jsonl` - 3건(en-US/zh-CN/ja-JP). AIS-002가 확인한 "카탈로그
  synonyms 11건 전부 ko-KR, 비-ko-KR 유사어 0건"이라는 사실을 그대로 반영했다 - 번역
  동의어를 지어내지 않고 `synonym_table_coverage: "NONE"` + 참고용
  `aspirational_concept_codes_via_llm`(보증 아님, LLM zero-shot 성공 시 기대값)만 남겼다.

작업 전 `src/meet_ai/ontology/catalog.v1.json`을 직접 조사했다(259개 concept, 228개
assignable, synonyms 11건 - AIS-002와 동일한 실측치). 각 샘플은 `input_text`/
`expected_intent`/`target_type`/`required_concept_codes`/`preferred_concept_codes`/
`excluded_concept_codes`/`forbidden_inferences`/`expected_search_targets`/
`ontology_gap_notes`/`clarification_expected`를 전부 기록한다. 카탈로그에 대응 개념이
없는 표현("AI 기술 보유", "친환경", "다국어 안내 솔루션", "물류 자동화 로봇", "스마트공장",

gap을 명시했다. `CHANNEL.ONLINE`처럼 `assignable=false` 구조 헤더가 필요한 질의
(BUYER-KO-002, "온라인 유통 가능한 제품")는 `clarification_expected: true`로 표시해
"임의 확정 대신 되묻기"가 필요한 사례를 Gold Set에 의도적으로 포함시켰다.

### AIS-005 - 자연어 질의 출력 Pydantic Schema

`ai/schemas/query_output.py`에 `QueryInterpretation`(intent/target_type/concept_codes/
required_conditions/preferred_conditions/excluded_concept_codes/confidence/
clarification_required/clarification_question)과 조건 1건용 `ConceptCondition`
(concept_code + 숫자형 comparator/value/value_max, TASTE.*/AROMA.*의 `data_type: NUMBER`
+ `validation.min/max`, ALCOHOL_LEVEL.*/PRICE_BAND.*의 `derived_bands`라는 실제 카탈로그
구조에 근거) Pydantic 모델을 정의했다.

`target_type`은 `candidate_generator.py`가 현재 2채널(EVENT_PRODUCT/EXHIBITOR)만
구현했다는 상태 대신 `.harness/contracts/domain-model.md` §7의 계약값 4종
(BOOTH/EVENT_PRODUCT/EXHIBITOR/PROGRAM)을 그대로 썼다 - 계약이 구현 상태보다 우선한다는
원칙(디스패치 지시사항의 근거 문서 순서와 일치).

검증 규칙(전부 실제 `pydantic.ValidationError`로 강제, 아래 TESTED에서 25건 실행 확인):

1. **허용 온톨로지 코드만 사용** - `meet_ai.ontology.load_catalog()`로 실제 카탈로그를
   조회해 존재 여부를 확인하고, 존재하되 `assignable=false`인 구조 헤더(`PRODUCT.ALL` 등)도
   조건으로 쓸 수 없게 거부한다(`backend/app/api/v1/endpoints/ontology.py`의
   `assignable_only` 필터와 동일 관례).
2. **confidence 0~1** - `Field(ge=0.0, le=1.0)`.
3. **개인정보 필드 금지** - 1차 방어선: `model_config = ConfigDict(extra="forbid")`로
   스키마를 닫아 `exhibitor_id`/`phone_number` 등 스키마 밖 필드 자체를 원천 차단.
   2차 방어선: `intent`/`clarification_question` 자유텍스트에 이메일·전화번호·UUID
   패턴이 섞이면 정규식 검증으로 거부.
4. **업체 ID·추천순위 직접 생성 금지** - 스키마 자체에 그런 필드가 없고, `extra="forbid"`가
   런타임 주입도 막는다. UUID 패턴 검증(3번과 공유)이 자유텍스트 안에 ID를 흘리는 것도 잡는다.
5. `clarification_required`/`clarification_question` 상호 일관성(필요한데 비어있으면
   거부, 불필요한데 값이 있으면 거부) - `model_validator`.

"원문에 없는 조건 생성 금지"(AGENTS.md §5)는 스키마 하나로 기계적 완전 검증이 불가능하다는
점을 모듈 docstring에 명시했다 - 이 규칙은 AIS-001 Gold Set의 `forbidden_inferences`와
AIS-003(Fallback 시나리오, 별도 태스크)에서 프롬프트·평가 단계로 보강해야 한다.

### AIS-006 - 하이브리드 검색 Provider 인터페이스

`backend/app/services/matching/search_provider.py`를 신규 생성했다(같은 디렉터리의
`candidate_generator.py`/`hard_filter_engine.py`/`feature_builder.py`/`orchestrator.py`/
`context_reranker.py`/`reason_generator.py`는 읽기만 하고 수정하지 않았다).

- `SearchProvider` - `@runtime_checkable` `Protocol`, `async def search(self, query, limit) -> list[SearchCandidate]`.
- `SearchQuery` DTO - `event_id`/`target_type`(domain-model.md §7의 4종 계약값)/`raw_text`/
  `required_concept_ids`·`preferred_concept_ids`·`excluded_concept_ids`(UUID, 기존
  `ChannelHit.matched_concept_ids`와 동일 관례)/`structured_filters`(제네릭 매핑 - 채널별
  price_max/moq_max 등을 전달)/`locale`.
- `SearchCandidate` DTO - `recommendable_id`/`rank`/`source_provider`/`matched_concept_ids`/
  `score_breakdown`.
- `SearchScoreBreakdown` DTO(§11.6) - `structured_score`/`keyword_score`/`semantic_score`/
  `data_quality_score`/`availability_score`/`final_score`/`reason_codes`, 전부 Optional -
  **값 계산은 Wave 2**(`GUEST_WEB_SEARCH_SCORE_V1`/`CONSUMER_SCORE_V1` 가중합).
- `CandidateCombiner` - 여러 Provider 결과를 합치는 단계의 **인터페이스만**(`Protocol`,
  구현 없음).
- `MockSearchProvider` - 테스트 더블(`canned_results`를 `limit`만큼 그대로 반환,
  `call_count`/`received_queries` 기록).

`StructuredSearchProvider`/`KeywordSearchProvider`/`VectorSearchProvider`/
`HybridSearchService`는 이름조차 빈 클래스 스텁으로 만들지 않았다 - 존재하지 않는 구현을
스텁으로 남겨 진행 중인 것처럼 보이게 하지 않기 위해 모듈 docstring 설명으로만 남겼다
(acceptance criteria가 "Protocol·DTO·Mock·후보 결합 인터페이스까지만"이라고 명시).

`candidate_generator.py`를 실제로 읽고 `reciprocal_rank_fusion`/`ChannelHit`/
`ChannelResult`의 실제 시그니처를 확인한 뒤, 모듈 docstring에 관계를 문서화했다: Wave 2의
`CandidateCombiner` 구현체는 `SearchCandidate` <-> `ChannelHit`/`ChannelResult` 변환
어댑터가 되어 **기존 `reciprocal_rank_fusion`을 그대로 호출**해야 하며, RRF 수식 자체를
이 파일에 재구현하지 않는다.
