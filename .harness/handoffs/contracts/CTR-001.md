# CTR-001

## 완료 내용

`.harness/contracts/domain-model.md`를 스텁 상태에서 실제 도메인 모델 레퍼런스로 완성했다. `docs/redesign-v2/` 26개 문서(`00-master-spec-v1.md`, `01-module-split-plan.md`, `04-integration-roadmap.md`, `web/W-1`~`W-10`, `kiosk/K-1`~`K-8`, `common/C-1`~`C-8`) 전체와 `backend/app/models/*.py`(identity/profile/exhibitor/matching/meeting/consent/core/ontology_refs) 전체, `backend/app/db/base.py`(스키마 상수), `backend/alembic/versions/*.py`(마이그레이션 체인)를 대조해 작성했다.

핵심 발견: 이번 재설계는 대부분 "기존 스키마 재발견·재계량"이며, 진짜 신규 스키마가 필요한 곳은 정확히 두 곳뿐이다 - `profile.saved_recommendable`(관심 저장, 이미 CTR-006으로 backlog에 있음)과 신규 `ai` 스키마 6개 테이블(`ai.source_document`/`extracted_attribute`/`content_approval`/`ai_execution_log`/`embedding_document`/`embedding_vector`) - 후자는 현재 backlog에 전용 태스크가 없다는 공백을 문서에서 명시적으로 드러냈다.

## 변경 파일

- `.harness/contracts/domain-model.md` (전면 재작성 - 유일한 소유 경로)

## 공개 인터페이스

없음 (문서 산출물, 코드/API 변경 없음).

## DB 변경

없음. 이 태스크는 DB를 직접 변경하지 않는다 - 문서가 식별한 신규 테이블 요구사항(`profile.saved_recommendable`, `ai.*` 6개)은 각각 CTR-006과 (아직 미배정인) 후속 CONTRACTS 태스크가 실제 마이그레이션을 담당한다.

## 테스트

해당 없음 - 문서 산출물이라 lint/type/unit/integration 테스트 게이트가 적용되지 않는다. 검증은 다음을 수동으로 확인했다: (1) 문서 내 모든 W/K/C 인용이 실제 파일에 존재하는 절/문장에 대응하는지 원문 대조, (2) 문서에 나열한 모든 테이블명·CHECK 제약값이 실제 `backend/app/models/*.py` 소스와 일치하는지 대조(예: `RECOMMENDED_ACTIONS` 10종, `FILTER_RESULT_TYPES` 8종, `role_code_allowed` 5종 등), (3) `backend/app/db/base.py`의 13개 스키마 상수와 마이그레이션 체인(0001~0008) 순서 확인.

## 알려진 제한

- `docs/db-erd-table-spec.md`(모델 docstring들이 1차 근거로 자주 인용하는 문서)는 이번 CTR-001의 근거 범위(`docs/redesign-v2/**` + `backend/app/models/*.py`)에 명시적으로 포함되지 않아 직접 읽지 않았다 - 다만 `backend/app/models/*.py`의 docstring이 이미 db-erd 절 번호를 충실히 인용하고 있어, 이 문서는 그 인용을 다시 옮기지 않고 실제 컬럼/제약을 직접 코드에서 확인하는 방식으로 갈음했다. db-erd 원문과의 미세한 필드 단위 불일치가 있다면 이 문서보다 실제 SQLAlchemy 모델 코드가 우선한다(이미 코드 자체가 그렇게 설계됨).
- 신규 `ai` 스키마 마이그레이션을 담당할 CONTRACTS 태스크가 `.harness/backlog.yaml`에 아직 없다 - Wave 1에서 이 공백을 인지하고 있어야 한다(§14에 명시).
- `role_code_allowed`(`DATA_REVIEWER`) 관련해서는 W-8이 "중간 우선순위 마이그레이션 필요"로 남겼던 것을 W-9/C-6이 "마이그레이션 불필요, 서비스 계층 권한 스코프로 대체"로 최종 재분류했다는 점을 문서에 명시했다 - 이 재분류를 놓치고 CHECK 확장 마이그레이션을 만들면 불필요한 작업이 된다.

## 다른 트랙이 해야 할 일

- **CTR-002(OpenAPI)**: 이 문서 §4(`saved_recommendable`)/§7(`recommendable`)/§9(`meeting` 3+4 테이블)/§11(`ai.*`)의 엔드포인트 목록(`04-integration-roadmap.md` 4단계 인용)을 그대로 스펙 초안의 입력으로 쓸 것.
- **CTR-003(온톨로지 계약)**: §5의 `concept`/`concept_revision`/`concept_synonym` 요약을 그대로 참고.
- **CTR-004(오류코드)**: §8의 `FilterResult.result` 8종(`PASS`/`FAIL`/`UNKNOWN`/`CONDITIONAL_PASS`/`MANUAL_REVIEW`/`TEMPORARY_BLOCK`/`POLICY_BLOCK`/`USER_EXCLUDED`)을 HTTP 오류코드 매핑의 정본 어휘로 사용할 것.
- **CTR-006(saved_recommendable 마이그레이션)**: §4의 확정 스키마(컬럼 5개 + UNIQUE 제약)를 그대로 구현하면 된다 - 추가 설계 불필요.
- **AI_SEARCH 트랙**: §8의 "재계량 결정"(가중치 재조정, `current_query` 컴포넌트, `KIOSK_SEARCH_SCORE_V1` 신규 정책)이 코드 레벨 작업임을 확인하고 Wave 2(AIS-GROUP-001)에서 반영.
- **모든 트랙 공통**: §9.2(상담 4테이블 비노출)와 §6(exhibition 20개 테이블)의 상태 요약표(§13)를 각 트랙의 owned_paths 작업 시 "이미 있는 테이블"과 "신규 필요"를 구분하는 1차 참조로 사용할 것.
