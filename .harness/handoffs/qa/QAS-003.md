# QAS-003 - 계약 검증 하네스 (OpenAPI/Migration/타입 일치)

## 착수 전 확인한 상태

작업 시작 시 `.harness/backlog.yaml`에서 의존 작업 CTR-002/003/004/005/008을 확인한
결과 전부 `status: READY`(미착수)였고, `.harness/contracts/openapi.yaml` /
`ontology.yaml` / `event-catalog.yaml` / `error-codes.yaml`은 전부 `DRAFT`
placeholder(`paths: {}`, `categories: []`, `events: []`, `codes: []`) 상태였다.
지시에 따라 완전히 차단하지 않고 **지금 DRAFT 콘텐츠 기준으로 검증 하네스 자체를
구현·실행**했고, 이 문서 끝에 CTR-002 등이 실제로 완료된 뒤 무엇을 다시 해야 하는지
명시한다.

## 완료 내용

`tests/api/` 하위에 QAS-003 acceptance("WAVE-1 §12.1 항목 자동화")의 8개 항목을
전부 자동화된 pytest 테스트로 구현했다. `infra/scripts/validate-harness`(하네스
자체 - state.json/backlog.yaml/locks.yaml 정합성)와 역할이 겹치지 않도록, 이쪽은
전적으로 "`.harness/contracts/*.yaml` 파일 **내용**이 유효한가"만 검사한다.

1. **OpenAPI 문법 유효성** (`test_openapi_syntax.py`): YAML 파싱 + 최소 구조
   (`openapi`/`info`/`paths` 키, `info.title`/`info.version`) + `openapi-spec-
   validator`를 이용한 실제 OpenAPI 3.x 스펙 검증(라이브러리 미설치 시
   `pytest.importorskip`로 우아하게 skip). `components`는 OpenAPI 스펙상 원래
   선택 항목이라 필수 검사에서 의도적으로 제외했다(과제 브리핑의 fallback 문구는
   언급했지만 실제 스펙 규칙과 상충하는 요구라 따르지 않았다 - 이유를 파일
   docstring에 남김).
2. **operationId 중복 검사** (`test_openapi_operation_ids.py`): 모든
   path×method에서 `operationId` 존재·중복 여부 검사.
3. **$ref 해석** (`test_openapi_schema_refs.py`): 문서 전체를 재귀 순회해 모든
   `$ref`를 찾아 JSON Pointer로 문서 내에서 해석 가능한지 확인(로컬 `#/...` ref만
   지원 - 이 저장소 계약은 단일 자기완결 파일이 원칙).
4. **오류응답 envelope 구조** (`test_openapi_error_envelope.py`): 2xx가 아닌 모든
   응답에 대해 `application/json` 스키마가 `{error:{code,message,request_id,
   details}}` 구조(중첩 `$ref` 포함 해석 후)를 따르는지 검사. 이 정확한 형태는
   임의로 정한 게 아니라 `.harness/backlog.yaml` CTR-002 acceptance 원문("오류
   응답은 {error:{code,message,request_id,details}} 구조로 통일")을 그대로 인용한
   것이다 - `docs/frontend-backend-ai-interface-spec.md` §4.4의 구버전 예시(`meta.
   request_id`, `error.field_errors`)와는 다른데, 그 문서는 하네스 이전 세션
   산출물이고 backlog.yaml의 CTR-002 acceptance가 이번 CONTRACTS 작업의 실제
   목표이므로 이쪽을 기준으로 삼았다(파일 docstring에 명시).
5. **온톨로지 YAML** (`test_ontology_contract.py`): 파싱 + 최상위 `status`/
   `categories` 키 존재 + (콘텐츠가 있을 때) 코드별 `label_ko`/`label_en`/
   `description`/`status`/`version` 필드 존재 + `parent` 참조 유효성. 필수 필드
   목록은 CTR-003 acceptance 원문("코드별 한국어/영어 라벨·설명·상위코드·동의어·
   상태·버전 필드 정의")에서 가져왔다. **주의**: `categories[].codes[]`라는 중첩
   구조 자체는 CTR-003이 아직 확정하지 않아 이 문서가 역산으로 추정한 것 -
   CTR-003이 실제로 다른 형태를 채택하면 `_iter_category_codes()`를 그에 맞게
   갱신해야 한다(아래 "다른 트랙이 해야 할 일" 참고).
6. **이벤트 카탈로그** (`test_event_catalog_contract.py`): 파싱 + `events` 키
   존재 + 이벤트 `name` 중복 없음.
7. **오류코드** (`test_error_codes_contract.py`): 파싱 + `codes` 키 존재 + 코드
   `code` 중복 없음.
8. **DB 마이그레이션 왕복** (`test_db_migrations.py`): `backend/tests/conftest.py`
   와 동일한 관례(`TEST_DATABASE_URL` env-gated, 동일 기본 URL, "연결 실패는 이유
   불문 SKIP" - 무관한 로컬 Postgres가 5432에 떠 있어도 인증 실패로 판정해 SKIP)를
   **파일을 건드리지 않고 tests/api/ 안에서 그대로 재구현**해서 `cd backend &&
   alembic upgrade head` → `downgrade -1` → `upgrade head` 왕복을 검사한다.

공유 로직(YAML 로더, JSON Pointer 리졸버, OpenAPI 순회 헬퍼)은 `tests/api/
_contracts.py`(테스트 파일 아님, `test_*.py` 패턴이 아니라 pytest가 수집하지 않음)에
모아 각 `test_*.py`가 acceptance 항목 하나씩에만 집중하게 했다. 디렉터리에
`__init__.py`가 없는 이 저장소 관례(`backend/tests/`와 동일)를 따라 상대 임포트 대신
`from _contracts import ...` 절대 임포트를 사용했다(pytest "prepend" import mode가
`tests/api/`를 sys.path에 직접 추가하므로 동작).

**생성 타입 일치성(Generated-type consistency)은 지시대로 이번 범위에서 제외**했다
- `openapi.yaml` → TS 타입 코드젠 파이프라인 자체가 아직 없다(Wave 2,
`packages/api-client`). 존재하지 않는 산출물을 검사하는 가짜 테스트를 만들지 않고
`tests/api/README.md`에 후속 과제로만 남겼다.

필드 4종 모두 존재하는 정상 케이스는 3개 테스트 모두 정상 PASS 확인.

## 작업 중 발견한 버그 (수정 완료)

`test_openapi_error_envelope.py`를 임시 위반 케이스로 스모크 테스트하던 중, 해석
불가능한 `$ref`가 섞여 있으면 `resolve_schema()`가 raw `KeyError`를 던져 테스트가
"FAILED"가 아니라 "ERROR"(처리되지 않은 예외)로 죽는 것을 발견했다. `$ref` 해석
관련 예외(`KeyError`/`IndexError`/`TypeError`/`ValueError`)를 잡아 위반 목록에
사람이 읽을 수 있는 메시지로 추가하도록 즉시 수정했고, 재실행으로 정상 동작(깨끗한
assertion 실패) 확인 완료 - 최종 파일에 이미 반영돼 있다.

## 알려진 제한

- CTR-002/003/004/005/008이 아직 착수 전이라, 지금 pass하는 6개 테스트는 "빈
  placeholder가 문법적으로 유효하다"만 검증한다 - 실제 계약 콘텐츠는 아직 전혀
  검증되지 않았다. **CTR-002/003/004/005/008이 완료되면 반드시 `cd tests/api &&
  ../../.venv/bin/pytest -v`(또는 동등한 pytest 환경)를 재실행해 지금 SKIP인 7개가
  실제로 PASS하는지 확인할 것.**
- `test_ontology_contract.py`의 `categories[].codes[]` 중첩 구조 가정은 CTR-003
  acceptance 문구에서 역산한 추정치다 - CTR-003이 실제로 다른 최상위 구조를
  채택하면(예: `categories`가 아니라 `concepts`를 바로 나열하는 flat 구조 등)
  `_iter_category_codes()`를 그 실제 구조에 맞게 고쳐야 정상 동작한다.
- `test_db_migrations.py`는 `sys.executable -m alembic`으로 alembic을 실행한다 -
  DB가 실제로 연결 가능한 CI/개발 환경에서는 그 인터프리터에 backend의 alembic/
  sqlalchemy/asyncpg 등 의존성이 설치돼 있어야 한다(이 환경에서는 `.venv/`에
  직접 설치해 확인했다). backend 자체 가상환경/CI 잡이 이미 이 의존성을 설치하는
  환경이라면 별도 조치가 필요 없다.
- $ref 리졸버는 로컬(`#/...`) 참조만 지원한다 - 외부 파일 참조는 이 저장소
  계약에서 쓰지 않는 것으로 가정했다(현재도 그렇다).
- API 계약 테스트(실제 배포된 엔드포인트가 openapi.yaml과 일치하는지)는 아직 실제
  엔드포인트가 없어(`.harness/state.json`의 `known_gap` 참고) 포함하지 않았다 -
  `tests/api/README.md`에 "향후" 항목으로 남김.
- 생성 타입 일치성 검사는 코드젠 파이프라인 부재로 스킵(가짜 테스트 없음, Wave 2
  후속 과제로만 기록).
