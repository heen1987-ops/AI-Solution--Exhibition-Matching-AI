# QAS-001 - 정적검사·시크릿 스캔 CI 통합

## 완료 내용

`.github/workflows/ci.yml`을 FND-003이 만든 3개 잡(`backend`, `meet-ai-core`, `ts-boundary`)을
그대로 둔 채 확장했다(대체 아님):

1. **`secret-scan` 잡(신규)**: gitleaks CLI(v8.30.1, linux_x64 고정 바이너리)를 GitHub
   릴리스에서 직접 내려받아 설치 후 `gitleaks detect`로 작업 트리를 스캔한다. 시크릿이
   발견되면 `--exit-code 1`로 빌드를 실패시킨다. `.gitleaks.toml` 같은 별도 규칙 설정
   파일 없이 gitleaks 기본 탐지 규칙만 사용한다.
   - marketplace의 `gitleaks/gitleaks-action`을 쓰지 않고 CLI를 직접 설치한 이유:
     해당 액션은 조직(Organization) 계정에서 사용할 때 라이선스(`GITLEAKS_LICENSE`)가
     필요할 수 있는데, 이 저장소가 개인/조직 어느 계정에 있을지 알 수 없어 라이선스
     유무와 무관하게 항상 동작을 보장하는 순정 CLI 방식을 택했다.
   - **베이스라인 필요성 발견**: gitleaks 기본 규칙으로 저장소를 실제 스캔해보니
     `docs/frontend-backend-ai-interface-spec.md`의 예시 `Idempotency-Key: <uuid>` 4곳이
     고엔트로피 문자열이라는 이유만으로 `generic-api-key` 규칙에 오탐되었다(실제 시크릿
     아님 - API 예시 문서의 더미 UUID). 베이스라인 없이 그대로 wiring했다면 QAS-001을
     "완료"로 처리한 순간 CI가 기존 코드 때문에 항상 빨간불이 되는 상태였을 것이므로,
     `.harness/reports/security/gitleaks-baseline.json`(gitleaks 네이티브 `--baseline-path`
     기능 - 별도 규칙 설정 파일이 아니라 스캔 결과 스냅샷)을 생성해 이 4건만 무시하도록
     구성했다. 새 시크릿이 추가되면 베이스라인에 없으므로 여전히 빌드가 실패한다.
     로컬에서 `gitleaks detect --baseline-path ...`로 실제 0건 확인 완료(아래 테스트 참고).
2. **`backend` 잡 확장**: `ruff check . --output-file .harness/reports/lint/ruff-backend.txt`,
   `pytest --junitxml .harness/reports/tests/pytest-backend.xml`로 결과를 리포트 경로
   규칙에 맞는 파일로 기록하고, `actions/upload-artifact@v4`(`if: always()`)로 CI 아티팩트에
   첨부한다. 실패 시에도 리포트가 남도록 `always()`를 사용했다.
3. **`meet-ai-core` 잡 확장**: `python -m unittest discover -s tests -v`의 출력을
   `set -o pipefail` + `tee`로 `.harness/reports/tests/meet-ai-unittest.log`에 남기고
   동일하게 아티팩트로 첨부한다(unittest는 pytest와 달리 junitxml 내장 기능이 없어
   `unittest-xml-reporting` 같은 추가 의존성 없이 텍스트 로그로 단순화했다 - 아래
   "알려진 제한" 참고).
4. `ts-boundary` 잡은 변경하지 않았다.

**중요 - 소유권 경로 관련 발견사항**: `.harness/locks.yaml`의 ownership 표는 `.github/**`를
FOUNDATION 트랙 전속으로 명시하고(23번 줄), QA_SECURITY 항목(59~62번 줄)에는 `.github/**`가

자체의 QAS-001 `owned_paths`(270~273번 줄)는 `.github/**`를 명시적으로 포함한다. 즉
`backlog.yaml`(태스크 정의)과 `locks.yaml`(AGENTS.md §4가 "유일한 정본"이라 선언한 문서)이

`backlog.yaml`의 명시적 owned_paths를 근거로 `.github/workflows/ci.yml`을 수정했지만, 이
불일치 자체는 하네스 데이터의 결함이므로 FOUNDATION/오케스트레이터가 `locks.yaml`을
갱신(QA_SECURITY 또는 공유 경로로 `.github/**` 반영)해 정본을 일치시킬 것을 권고한다.

## 테스트

로컬 venv(Python 3.12)로 CI가 실행할 각 단계를 개별 검증했다(GitHub Actions 자체는
이 환경에서 실행 불가하므로 각 CLI 커맨드를 동일 인자로 로컬 실행):

- YAML 유효성: `python3 -c "import yaml; yaml.safe_load(open('.github/workflows/ci.yml'))"`
  → 예외 없이 통과.
- gitleaks 설치·동작: v8.30.1 darwin_arm64 바이너리(로컬 검증용, CI는 linux_x64 사용)로
  `gitleaks detect --source . --no-git --report-format json --report-path ... --redact=0`
  실행 → 기존 4건(docs 예시 UUID) 발견 확인 → 이를 베이스라인으로 저장 →
  `gitleaks detect --baseline-path .harness/reports/security/gitleaks-baseline.json ...`
  재실행 → `no leaks found`, `exit code: 0` 확인.
- `ruff check . --output-file <path>`: 정상 상태에서 파일 생성 + exit 0 확인. 임시로
  `backend/app/main.py`에 미사용 import를 주입해 exit 1 + 위반 내용이 파일에 기록됨을
  확인한 뒤 즉시 원복(`git diff --stat backend/app/main.py` 결과 없음 확인).
- `pytest --junitxml <path>`: 정상 실행되고 유효한 JUnit XML(`<testsuites>`)이 생성됨을
  확인. 결과는 90 passed, 11 skipped(AIS-002 작업으로 추가된 7건 포함, 회귀 없음).
- `meet-ai-ontology validate` + `python -m unittest discover -s tests -v | tee ...`:
  `OK ontology 1.0.0: 259 concepts, 11 synonyms, 7 relations`, `Ran 23 tests ... OK`,
  로그 파일 정상 생성 확인.

CI 자체가 실제 GitHub Actions 러너에서 트리거되어야 최종 확인되지만(이 환경에서는
불가), 각 스텝의 커맨드·인자·종료 코드 동작은 모두 동일한 방식으로 로컬 재현·검증했다.

## 알려진 제한

- `.harness/reports/**`에 기록되는 lint/test 산출물은 **CI 러너 로컬에만 기록되고
  저장소에 커밋되지 않는다** - `actions/upload-artifact`로 GitHub Actions 아티팩트로만
  보존된다. "저장소에 영구 보관"까지 요구한다면 별도의 커밋-백(commit-back) 잡이
  필요한데, 동시 PR 간 경합·봇 커밋 정책·무한 루프 방지 등 부가 복잡도가 이번 태스크
  범위 대비 과도하다고 판단해 구현하지 않았다. 필요 시 후속 작업으로 제안한다
  (아래 "다음 권장 작업" 참고).
- `meet-ai-core` 잡은 pytest의 `--junitxml` 같은 표준 리포트 포맷 대신 텍스트 로그(tee)만
  남긴다 - `unittest`는 내장 JUnit XML 출력이 없고, `unittest-xml-reporting` 같은 추가
  런타임 의존성을 도입하는 것은 이번 범위에서 과한 것으로 판단했다.
- gitleaks는 작업 트리(`--no-git`)만 스캔한다 - 과거 커밋 이력에 남아있다가 이후
  삭제된 시크릿까지 잡아내는 전체 히스토리 스캔은 아니다("기본 시크릿 스캔" acceptance
  기준에 맞춰 범위를 최소로 유지했다). 전체 히스토리 스캔이 필요하면 `--no-git` 제거 +
  `fetch-depth: 0` 체크아웃으로 확장 가능하나, 기존 커밋에 실제 시크릿이 있었을 경우
  최초 실행에서 대량 오탐/실탐이 쏟아질 수 있어 별도 검토 후 진행 권장.
- 위 "중요 - 소유권 경로 관련 발견사항"에 적은 `locks.yaml` vs `backlog.yaml`의
  `.github/**` 소유권 불일치는 아직 해소되지 않았다.

## 다른 트랙이 해야 할 일

- **FOUNDATION 트랙**: `locks.yaml`의 `.github/**` 소유권 표기를 `backlog.yaml`
  QAS-001 정의와 일치시킬지(QA_SECURITY 추가 또는 공유 경로로 명시) 결정하고 갱신.
- **BACKEND 트랙**: `backend/pyproject.toml`에 향후 mypy를 도입하면(AGENTS.md §3의
  ADR 절차를 거쳐) `backend` 잡에 타입체크 스텝과 그 결과의 리포트 경로
  (`.harness/reports/lint/mypy-backend.txt` 등)를 추가로 배선해야 한다 - 이번
  범위에는 포함하지 않았다(FND-003 노트에 이미 "mypy 미구성"으로 기록됨).
- **CONTRACTS 트랙**: `docs/frontend-backend-ai-interface-spec.md`의 예시 UUID들이
  실제로는 시크릿이 아니지만, 향후 이 문서에 진짜 시크릿과 헷갈릴 수 있는 값을 추가할
  때는 `gitleaks-baseline.json`에 새 항목이 없으면 CI가 실패한다는 점을 인지할 것.
